Part I — Understanding IDEs

Chapter 1What Is an IDE?

1.1 The workshop idea

Imagine you want to build a wooden chair. You could do it with a hand saw, a hammer, a ruler and a pencil, each kept in a different shed across the garden. Or you could do it in a workshop where the saw, hammer, ruler and pencil are on one bench, the lights are good, and a helper hands you the right tool at the right moment.

An IDE is that workshop, but for writing programs.

KEY WORD IDE

IDE stands for Integrated Development Environment. Integrated means "joined together into one". Development means "making software". Environment means "the place where you work". So an IDE is one place where all the tools for making software are joined together.

You can write a program in the simplest text editor, such as Notepad. Programs have been written that way for decades. But then you must save the file, open a separate window, type a long command to turn your code into a program, run it, and read the errors in yet another window. Each step is small. Together they are slow and tiring.

An IDE puts it all in one window. You type your code, press one green button, and the program runs.

1.2 Editor versus IDE

Many people mix these two up, so let's be clear.

Text editor IDE

Colouring words (syntax highlighting) Often Yes
Press one button to build and run No Yes
Understands your code (suggests, finds errors) No Yes
Debugger built in No Yes
Terminal built in Rarely Yes
Starts fast, small Yes Heavier
IN PLAIN WORDS In plain words

A text editor is a pencil. An IDE is a pencil, a ruler, an eraser, a calculator and a teacher looking over your shoulder, all in one.

1.3 A short history

  • 1950s to 1970s. Programmers wrote code on punch cards. There was no screen. You handed the cards in and came back hours later to see if it worked.
  • 1980s. Programs like Turbo Pascal (1983) put an editor and a compiler into one program. You could write, run and fix code in seconds. This was the first popular IDE.
  • 1990s. Visual Studio and Delphi added drag-and-drop windows, debuggers and project management.
  • 2000s. Eclipse and IntelliJ IDEA added code understanding: the IDE learned to suggest the next word and rename things safely.
  • 2010s to today. JetBrains made tools for each language. CLion is their IDE for C and C++. Microsoft's VS Code popularised the idea of a lightweight editor extended with plug-ins and a language server (you will meet this in Chapter 2).

1.4 What CLion does, and why we built NOVA

CLion is a professional IDE for C and C++. It has a project tree, a smart editor, CMake support, a debugger, a terminal and a dark, modern look. It is excellent. But it is paid software, and it is closed: nobody outside JetBrains can see how it is built.

Team NOVA decided to build our own IDE with the same workflow: the same layout, the same shortcuts, the same ideas. The goals were:

  1. Free to use inside the team, forever.
  2. Understandable. Every file small enough to read in one sitting.
  3. A teaching tool. If you build an IDE, you learn how all your other tools work.
WHY? Why build your own IDE at all?

Because an IDE touches almost every big idea in programming: files, processes, text, windows, networks of messages, compilers and debuggers. Building one is like building an engine to learn how cars work. You will not beat a professional car factory. But you will never again be confused by what is under the bonnet.

WATCH OUT Watch out

NOVA is not a copy of CLion's code. CLion's program files are private and protected by law. NOVA was designed from public documentation, common knowledge and the team's own ideas, and it uses open-source building blocks (Monaco, Electron, xterm.js, clangd, gdb). This is both legal and a better way to learn.

Chapter 2The Parts of an IDE

An IDE is a team of small helpers. Each helper does one job well. When you understand the helpers, no IDE will ever look mysterious again. Let's meet them one by one. For each we answer three questions: What is it? Why does it matter? What happens if it is missing?

2.1 The code editor

What it is. The big area where you type code. A good code editor does more than store letters. It colours keywords, matches brackets, lets you fold blocks, finds and replaces text, and handles huge files without slowing down.

Why it matters. You will look at this area for 95 percent of your working day. If it is slow, ugly or clumsy, everything feels bad.

If it were missing. You would have nothing to type into. There is no IDE without an editor.

KEY WORD Syntax highlighting

Colouring different kinds of words differently (for example keywords orange, strings green, numbers blue). It lets your eyes see the structure of the code instantly. A missing quote mark shows up because everything after it turns green.

NOVA does not build an editor from nothing. That would take years. It uses Monaco, the open-source editor that powers VS Code. We add our own colours, snippets and features on top.

2.2 The project tree

What it is. The panel on the left that shows your folders and files as a tree you can open and close.

Why it matters. Real programs have tens or thousands of files. You need a map. The tree is that map. It also lets you create, rename and delete files without leaving the IDE.

If it were missing. You would have to open files by typing their names, and you would lose track of how your project is organised.

2.3 Tabs

What they are. Each open file gets a tab at the top, like pages in a web browser.

Why they matter. You constantly jump between a few files. Tabs make that one click. A small dot on a tab warns you that the file has unsaved changes.

2.4 The build system

What it is. The part that turns your code into a program you can run. It starts the compiler and the linker for you, with the right options, and reports problems.

Why it matters. Building a big C++ program by hand needs a very long command. Get one option wrong and it fails. The build system remembers the recipe so that you press one button.

If it were missing. You would copy and paste long commands into a terminal every time you changed one line.

NOVA's build system uses CMake to describe the recipe, Ninja to follow it quickly, and g++ (the compiler) to do the real translation. Chapter 3 explains each.

2.5 The run console

What it is. A panel at the bottom that shows what your program prints and lets you type input back to it.

Why it matters. Programs talk to you through text. If you cannot see it, you cannot test your work.

2.6 The problems panel and error squiggles

What it is. A list of mistakes and warnings, plus red or yellow wavy lines under the exact words that are wrong.

Why it matters. Mistakes are normal. What matters is how fast you find them. A wavy line under the word is far faster than reading line 4,287 of a log.

2.7 The language server (code intelligence)

What it is. A separate program that actually understands your C++. When you type std::vec it knows you might want vector. When you hover over a function it shows its documentation. When you press a key on a name it can jump to where it was defined.

Why it matters. This is the biggest difference between a plain editor and an IDE. It makes you faster and catches errors before you even build.

If it were missing. You could still write code, but you would type everything yourself and find every mistake only after building.

KEY WORD Language server and LSP

A language server is a program that understands one programming language. LSP (the Language Server Protocol) is the agreed set of messages an editor and a language server use to talk. Because the messages are standard, one server (like clangd for C and C++) works in many editors. NOVA uses clangd.

2.8 The debugger

What it is. A tool that lets you pause a running program at a chosen line, look at the values of its variables, and move forward one step at a time.

Why it matters. Printing messages to find a bug is like searching a dark room with a match. A debugger turns on the light.

If it were missing. You would guess. Programmers have lost days of their lives to guessing.

KEY WORD Breakpoint

A breakpoint is a mark on a line that says "stop here when you get to it". It shows as a red dot in the margin.

2.9 The terminal

What it is. A real command line inside the IDE.

Why it matters. Some jobs are easiest from the command line: running git, listing files, trying a command. Having it inside the IDE means you never switch windows.

2.10 Search and navigation

What it is. Tools to find things fast: find in the current file, find across the whole project, jump to a file by typing a few letters, jump to a function by name.

Why it matters. In a big project, finding code takes more time than writing it. NOVA copies JetBrains' famous double-Shift "Search Everywhere".

2.11 The status bar and settings

What they are. A strip at the bottom with small facts (line and column, which compiler, which language), and a settings window for fonts, themes and options.

Why they matter. Small facts prevent big confusion. You always know which compiler is in use and where your cursor is.

2.12 All the parts together

The magic of an IDE is not any single part. It is that all the parts share information. The compiler's error appears as a wavy line in the editor. The debugger's current line is highlighted in the editor. The tree opens files in the editor. Everything is connected.

Chapter 3From Code to a Running Program

To build an IDE for C and C++ you must understand what happens between "I typed some code" and "the program runs". This chapter explains it in simple steps. It also answers a common question: what is an interpreter, and is NOVA one?

3.1 Your computer only speaks one language

A computer's brain, the CPU, understands only machine code: long lists of numbers. Nobody wants to write that. So humans invented programming languages like C++, which are readable. A special program must translate our readable code into machine code. There are two ways to do the translation.

3.2 Compilers and interpreters

KEY WORD Compiler

A compiler translates your whole program into a separate machine-code file once, before it runs. Afterwards you run the file as many times as you like, very fast. C and C++ use compilers.

KEY WORD Interpreter

An interpreter reads your program and carries out the instructions as it goes, one by one, with no separate file. Starting is instant, but running is usually slower. Python and (originally) JavaScript use interpreters.

Think of a speech. A compiler is a translator who takes your whole written speech home, translates it carefully, and gives you a finished translated copy. An interpreter is a translator who stands beside you and translates every sentence live as you speak.

WHY? Why does this matter for an IDE?

The folder NOVA lives in is called "C Interpreter" but NOVA is not an interpreter. It is an IDE that drives a compiler. This matters because it decides what the IDE must do: when you press Run, it must start the compiler, wait, check for errors, then start the new program. An interpreter-based IDE would simply feed your code to the interpreter. (JavaScript, which NOVA itself is written in, is actually a hybrid: modern browsers interpret first and compile the busy parts. See the figure.)

3.3 The four steps inside a C++ compiler

When you type g++ main.cpp -o hello.exe, four stages happen quietly. You must know them because every error you will ever see comes from one of them.

  1. Preprocessing. Lines that begin with #, like #include <iostream>, are handled first. #include simply pastes the contents of another file in. After this step, your file is one very long piece of text.
  2. Compiling. The compiler checks the grammar of your code and translates it into assembly, a low-level readable form of machine code. Syntax errors ("missing semicolon") come from here.
  3. Assembling. The assembler turns assembly into object code (main.o): real machine code, but with gaps where it needs to find other pieces.
  4. Linking. The linker joins your object files and libraries into one finished program, filling in the gaps. "Undefined reference" errors come from here.
WHAT IF IT WERE DIFFERENT? What if there were no linker?

Large programs are written in many files. Each file is compiled on its own, so each has gaps where it calls functions defined elsewhere. Without a linker, nothing would join the files. You would be forced to write all your code in a single file. The linker is what makes big projects possible.

3.4 How does an interpreter really work?

Even though NOVA is not an interpreter, you should know how one works. It is a famous exercise and you will build a tiny one in the JavaScript chapter. An interpreter has three stages.

  1. Lexer (or tokenizer). It cuts the text into small meaningful pieces called tokens: numbers, plus signs, names.
  2. Parser. It arranges tokens into a tree that shows the structure, called an AST (Abstract Syntax Tree). The tree is how the machine knows that 2 * 3 happens before adding 1.
  3. Evaluator. It walks the tree from the bottom up, calculating as it goes.
WHY? Why a tree and not just a list?

Because meaning depends on grouping. In 1 + 2 * 3 the answer is 7, not 9, because multiplication binds tighter. A flat list of tokens cannot show grouping. A tree can. Compilers, language servers and IDE features like "rename" all use trees like this. When clangd highlights a word it has already built the tree of your file.

3.5 So where does an IDE fit?

An IDE is the manager that calls all these workers for you. The flowchart shows what NOVA does when you press Run. Notice that NOVA never translates any code itself. It starts other programs (cmake, g++, your program), listens to what they print, and shows the result nicely. That is the central idea of this whole book:

An IDE is a friendly control panel for other programs.

Chapter 4How NOVA Is Designed

Now we look at the blueprint of NOVA. Do not worry if some words are new; each is explained here and again in the language chapters.

4.1 Two kinds of processes

NOVA is built with Electron. Electron is a toolkit that lets you build desktop programs out of web technology (HTML, CSS and JavaScript). Chrome and VS Code are built this way.

An Electron program is split into two kinds of processes. A process is a running program with its own private memory.

  • The main process (our file main.js) is the engine room. It runs on Node.js, so it is allowed to touch files, start other programs and open windows.
  • The renderer process (our files in the renderer folder) is the window you see. It is a web page, written in HTML, CSS and JavaScript. For safety it is not allowed to touch your disk or start programs.

Between them sits a thin bridge (preload.js) that decides exactly which doors are open.

WHY? Why split it in two?

Safety and stability. A web page can show content from anywhere. If it had full power over your computer, one bad page could delete your files. Splitting the powers means the window can only do what the bridge allows. It also means that if the window freezes, the engine room keeps running.

WHAT IF IT WERE DIFFERENT? What if the window could touch the files directly?

It would work, and it would be simpler to write. But any script that sneaked into the window (for example from a malicious file you opened) could read, change or delete anything on your computer. The two-process design closes that door. Electron's own guidelines recommend it.

4.2 How the two sides talk: IPC

The window and the engine room are separate programs, so they talk by sending messages. This is IPC, Inter-Process Communication.

In NOVA you will see lines like await nova.read(path). That one line travels through the bridge to the main process, which reads the file from disk, and the answer travels back. The word await means "wait here until the answer arrives, but keep the window alive".

4.3 NOVA also talks to other programs

The main process does not only read files. It starts helper programs and pipes text to and from them. A pipe is a one-way channel for text between two programs, like a tube.

Chapter 5The Languages Behind NOVA

NOVA is a team of languages, each with its own job. Using the right language for each job is what makes the program small.

5.1 HTML: the skeleton

HTML (HyperText Markup Language) describes what is on the screen: a toolbar, a sidebar, a button. It is not a programming language, because it makes no decisions. It is a markup language: it labels things. In NOVA, index.html lists every panel.

5.2 CSS: the skin

CSS (Cascading Style Sheets) says how things look: colours, sizes, spacing, fonts. NOVA's dark and light themes are just two sets of colours in styles.css. Change a colour in one place and the whole IDE changes.

5.3 JavaScript: the brain

JavaScript is a real programming language. It makes decisions and reacts to clicks, key presses and messages. Most of NOVA's logic is JavaScript: opening tabs, running builds, talking to clangd and gdb.

WHY? Why JavaScript and not C++ for the IDE itself?

You could write an IDE in C++. Many do. But JavaScript with Electron gives us a ready-made window system, text editor (Monaco), terminal (xterm.js) and fast screen drawing. We write far less code, and JavaScript lets us change something and see the result in seconds. The price is more memory use. For a team tool, that is a good trade.

5.4 Node.js and Electron: the engine room

Node.js is JavaScript that runs outside a browser, so it can read files, start programs and use the network. Electron bundles Node.js with a browser engine to create desktop applications. NOVA's main.js and preload.js use them.

5.5 C and C++: the cargo

C and C++ are the languages NOVA is built for. They are not used to build NOVA's window, but you need to know them well to test, use and extend the IDE: you will write C and C++ programs to try every feature. They are also the language of the tools NOVA drives (gcc, g++, clangd and gdb are themselves written in C and C++).

5.6 CMake and JSON: the glue

CMake is a small language for describing how to build C and C++ projects. NOVA writes CMake files for new projects and runs CMake for you. JSON is a simple text format for data. NOVA uses it for settings, for the compile database and for every message exchanged with clangd.

5.7 Helpers you will meet briefly

  • GDB/MI and LSP: "mini languages" of messages. We study them in Chapter 13.
  • Batch (Launch NOVA.bat) and PowerShell: small scripting languages used to start the program.
  • Python: not part of NOVA itself. The book's own build script uses it to turn this text into the PDF you are reading.

5.8 The learning order

The language chapters are in the order that makes learning easiest:

  1. HTML (easiest, you see results at once)
  2. CSS (makes it pretty)
  3. JavaScript (your first real programming)
  4. Node.js and Electron (power tools)
  5. C (the foundation of low-level computing)
  6. C++ (C with superpowers)
  7. CMake (builds)
  8. JSON and protocols (how programs talk)

Chapter 6HTML: The Skeleton

6.1 What HTML is, in one minute

Every web page you have ever seen, and the window of every Electron program, starts as an HTML file. HTML tells the computer what things are on the page: "this is a heading", "this is a button", "this is a list".

KEY WORD HTML

HyperText Markup Language. Markup means you wrap pieces of text in tags that label them. HTML does not calculate or decide. It only describes.

Think of a school report. The title is big and centred. Below are paragraphs. There may be a table and a picture. HTML is the way you tell the computer "this part is the title, this part is a paragraph, this part is a table".

6.2 Your first page

Create a file called hello.html. Type this exactly:

HTML
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8" />
  <title>My First Page</title>
</head>
<body>
  <h1>Hello, NOVA!</h1>
  <p>This is my first web page.</p>
</body>
</html>

Double-click the file. Your browser opens it. You just made a page.

Let's read it line by line.

Line Meaning
<!doctype html> "This page uses modern HTML." Always the first line.
<html lang="en"> The root. Everything lives inside it. lang says the page is in English.
<head> Information about the page that is not shown in the window.
<meta charset="utf-8" /> Tells the browser how to read letters, so that symbols and other languages show correctly.
<title> The name shown on the browser tab.
<body> Everything that you actually see.
<h1> A top-level heading.
<p> A paragraph.
WHY? Why do tags come in pairs?

A tag like <p> is an opening tag and </p> is the closing tag. The pair says where the paragraph starts and where it ends. Without the closing tag the browser would have to guess, and it would often guess wrong, making the whole page strange. The text between is the content. The whole thing together is an element.

WHAT IF IT WERE DIFFERENT? What if you forget `<!doctype html>`?

The browser switches to quirks mode, an old compatibility mode from the 1990s. Sizes and spacing behave differently, and your page looks subtly wrong. This is a good example of a tiny line that prevents a big headache. NOVA's index.html starts with it.

6.3 The tree behind the page

When the browser reads your HTML it builds a tree in memory called the DOM (Document Object Model). Every element is a branch, every piece of text a leaf.

WHY? Why does the tree matter?

Because JavaScript does not edit the text of your HTML file. It edits the tree. When NOVA opens a tab, JavaScript adds a new branch to the tree, and the browser redraws. Understanding the tree is the key to understanding every web program.

6.5 Attributes, ids and classes

An attribute gives extra information to a tag: <a href="...">. Two attributes are the most important in all of web programming:

  • id gives an element a unique name: <div id="sidebar">. Only one element on the page may have a given id. JavaScript uses ids to find elements: document.querySelector('#sidebar').
  • class gives an element a group name: <button class="ib sm">. Many elements may share a class. CSS uses classes to style whole groups at once.
WHY? Why both id and class?

An id is like a passport number: unique to one person. A class is like a school uniform: many people wear it. When you need to reach exactly one element (the Run button) use an id. When you want to style many (all small icon buttons) use a class. Mixing them up is a very common beginner error.

Data attributes

You can invent your own attributes starting with data-. NOVA uses them to remember which panel a button opens:

HTML
<button class="sb" data-panel="project" title="Project (Alt+1)">…</button>
<button class="sb" data-bottom="problems" title="Problems (Alt+6)">…</button>

JavaScript reads them back with button.dataset.panel. This lets one small piece of code serve many buttons, instead of writing a separate function for each.

6.6 Page layout with semantic tags

Old pages used <div> for everything. Modern HTML has tags that say what they are:

HTML
<header>  top bar or title area  </header>
<nav>     a group of navigation buttons  </nav>
<aside>   a sidebar  </aside>
<main>    the main content  </main>
<section> a themed group of content  </section>
<footer>  bottom strip  </footer>

NOVA's skeleton uses exactly these: a <header id="titlebar">, a <nav class="stripe">, an <aside id="sidebar">, a <main id="center">, a <section id="bottom"> and a <footer id="status">. Look back at the anatomy figure in Chapter 2: those seven regions are these tags.

WHY? Why use semantic tags instead of div?

For meaning. A screen reader can say "navigation" or "main content" and let the user jump there. Search engines understand the page better. And you will understand your own file better when you return to it in six months. Meaning costs nothing and helps everyone.

6.7 The hidden attribute, and a real NOVA bug

HTML has a built-in attribute called hidden. Any element with hidden is not shown:

HTML
<div id="bottom" hidden>…the bottom panel…</div>

NOVA turns panels on and off by setting element.hidden = true or false from JavaScript. But there is a trap that cost the team an hour.

WHAT IF IT WERE DIFFERENT? What if you also give that element a CSS `display` rule?

If your CSS says #bottom { display: flex; }, that rule beats the browser's built-in "hidden means display none" rule, and the panel stays visible even though it has the hidden attribute! The fix is one line of CSS that makes hidden always win:

[hidden] { display: none !important; }

This line is the very first line of NOVA's styles.css. Now you know why.

6.8 Scripts and style sheets

An HTML file loads other files with two tags:

HTML
<link rel="stylesheet" href="styles.css" />   <!-- the CSS (looks) -->
<script src="app.js"></script>                <!-- the JavaScript (behaviour) -->

Where you put the <script> matters. NOVA's scripts sit at the bottom of the body. Why? Because the browser reads the page top to bottom. If a script runs before the elements it needs exist, document.querySelector finds nothing. At the bottom, everything above already exists.

WHY? Why does the order of NOVA's scripts matter?

In NOVA's index.html, the xterm terminal library is loaded before Monaco's loader. The reason is subtle: Monaco's loader creates a global function called define. The xterm library checks for define and, if it finds one, registers itself in a different way that does not create the global Terminal that NOVA needs. Loading xterm first avoids the clash. This was a real bug found during development, and it is a good lesson: order of scripts can change behaviour.

6.9 SVG: drawing with text

SVG (Scalable Vector Graphics) lets you draw shapes with HTML-like tags. Every icon in NOVA and every diagram in this book is SVG. It is just text, it stays sharp at any size, and you can colour it from CSS.

HTML
<svg viewBox="0 0 120 60" width="240">
  <rect x="5" y="5" width="110" height="50" rx="8" fill="white" stroke="black" stroke-width="3"/>
  <circle cx="30" cy="30" r="12" fill="black"/>
  <text x="50" y="36" font-size="16">NOVA</text>
  <path d="M95 20 l10 10 l-10 10" fill="none" stroke="black" stroke-width="3"/>
</svg>

NOVA's icons are described by a single path string such as M4.5 3l8 5-8 5z (a triangle: move to a point, line to the next two, close). The whole icon set in icons.js is thirty lines.

WHY? Why SVG icons and not picture files?

A picture file (PNG) has a fixed number of pixels: it gets blurry when enlarged and cannot change colour. SVG is maths: it stays crisp at any size, and by writing stroke="currentColor" the icon automatically takes the colour of the text around it, so a single icon works in both dark and light themes.

6.10 Accessibility in one page

About one person in six has some disability. Good HTML helps them for free:

  • Use real <button> tags for buttons (not a styled <div>). Keyboard users can reach and press them.
  • Always give images alt text and buttons a title or label.
  • Use headings in order.
  • Make sure text has strong contrast against its background.
  • Make everything usable with the keyboard alone. (A programming tool should! NOVA has shortcuts for almost everything.)

Chapter 7CSS: The Skin

7.1 What CSS does

If HTML is the skeleton, CSS is the skin, clothes and make-up. It decides colours, sizes, spacing, fonts and where things sit on the screen.

KEY WORD CSS

Cascading Style Sheets. A list of rules. Each rule says: for elements that match this selector, set these properties. "Cascading" means that when rules clash, there is a fair order for deciding which one wins.

7.2 Your first rule

CSS
h1 {
  color: black;
  font-size: 28pt;
}

Parts of a rule:

  • h1 is the selector: which elements to style.
  • Between the braces { } is the declaration block.
  • color: black; is one declaration: a property (color), a colon, a value (black) and a semicolon.

Three ways to add CSS to HTML:

  1. External file (best): <link rel="stylesheet" href="styles.css" />. NOVA does this.
  2. A <style> block inside the page head.
  3. Inline on one tag: <p style="color:red">. Quick but messy.
WHY? Why keep CSS in its own file?

Because one file can style many pages, the browser remembers (caches) it, and you change the look of the whole program in one place. Mixing CSS into HTML is like writing instructions on every single brick of a house.

7.3 Selectors: choosing what to style

Selector Picks Example
p every <p> p { margin: 0; }
.tab every element with class tab .tab { padding: 0 12px; }
#sidebar the one element with id sidebar #sidebar { width: 280px; }
.tab.active has both classes .tab.active { color: black; }
.node:hover when the mouse is over it .node:hover { background: grey; }
#tabs .tab a .tab inside #tabs
button:disabled disabled buttons opacity: .35;
li:nth-child(even) every second item zebra stripes

7.4 Units and colours

Sizes: px (pixels, fixed), % (percentage of the parent), em/rem (relative to font size), vh/vw (percent of the window height/width), pt (points; used in this book for text).

Colours can be names (black), hex codes (#3574f0), or rgb(53, 116, 240). A hex code is red, green and blue written in base 16: #RRGGBB. An 8-digit code adds transparency: #ffffff1c is white at about 11 percent opacity (NOVA uses it for hover highlights).

7.5 The box model: everything is a box

This is the single most important idea in CSS. Every element is a rectangular box made of four layers.

CSS
.node {
  padding: 4px 8px;        /* space INSIDE the border */
  border: 1px solid grey;  /* the line */
  margin: 2px 0;           /* space OUTSIDE the border */
}
WHY? Why does NOVA say box-sizing: border-box?

By default, width: 100px sets only the content width, and padding and border are added on top, so the box ends up wider than 100px. That surprises everyone. One of the first rules in NOVA's CSS is * { box-sizing: border-box; }, which makes width include padding and border. A 100px box stays 100px. Almost every modern site starts with this line.

WHAT IF IT WERE DIFFERENT? What if you skip it?

Imagine a panel set to width: 100% with padding: 10px. Without border-box it is 100% plus 20px wide, so it sticks out past the window and a horizontal scrollbar appears. This is one of the most common layout bugs in the world.

7.6 Variables: change the whole look in one place

CSS has custom properties (variables). You define them once and use them everywhere with var():

CSS
:root {
  --bg: #1e1f22;      /* main background */
  --text: #dfe1e5;    /* text colour */
  --accent: #3574f0;  /* blue highlights */
}
body  { background: var(--bg); color: var(--text); }
.btn.primary { background: var(--accent); }

:root means "the top of the page", so the variables are available everywhere. Now watch the trick that gives NOVA its themes:

CSS
:root[data-theme="light"] {
  --bg: #ffffff;
  --text: #1e1f22;
}

When JavaScript sets document.documentElement.dataset.theme = 'light', the second block takes over, every var(--bg) changes, and the entire IDE is light. No other code is needed.

WHY? Why variables instead of typing the colours everywhere?

NOVA uses its background colour in dozens of places. With variables, changing it is a one-line edit. Without them you would hunt through the file, miss three spots, and end up with an ugly mismatch. Variables are also what make themes (dark, light, high-contrast) cheap to add.

7.7 Layout, part 1: Flexbox

Flexbox arranges items in a row or a column and spreads out the space for you. It is how almost every toolbar is made.

CSS
.toolbar {
  display: flex;                 /* turn flexbox on for the children */
  align-items: center;           /* line them up vertically */
  justify-content: space-between;/* push first and last to the edges */
  gap: 6px;                      /* space between items */
}

Key flexbox properties:

Property What it controls
display: flex Starts flexbox on the parent
flex-direction row (sideways) or column (downwards)
justify-content Spacing along the main axis
align-items Alignment across the main axis
gap Space between items
flex: 1 "Take all the leftover space"

NOVA's tab bar, status bar, toolbar, bottom-panel header and the Debug panel's button row are all flexbox. The central column (#center) uses display: flex; flex-direction: column so the tabs sit on top of the editor, which has flex: 1 and grows to fill the rest.

7.8 Layout, part 2: Grid

Grid places things in rows and columns at once. It is perfect for whole-window layouts.

CSS
#app {
  display: grid;
  grid-template-rows: 40px 1fr auto auto 24px;  /* title, workspace, splitter, bottom, status */
  height: 100vh;
}
#workspace {
  display: grid;
  grid-template-columns: 40px 280px 4px 1fr;    /* stripe, sidebar, splitter, editor */
}

The magic unit is fr (a fraction of the free space). 1fr means "whatever is left after the fixed sizes".

WHY? Why 1fr for the editor?

When you resize the window, the title bar must stay 40px tall and the stripe 40px wide, while the editor absorbs all the change. 1fr expresses exactly that. Doing this with percentages would need maths and would break at odd sizes.

CSS variables in the grid: resizable panels

NOVA lets you drag the sidebar edge. The grid width is written as var(--side-w, 280px). While you drag, JavaScript simply changes the variable:

JavaScript
document.documentElement.style.setProperty('--side-w', newWidth + 'px');

The grid recalculates by itself. No loops, no manual resizing of children.

7.9 Position, overflow and layers

  • position: absolute; inset: 0; stretches an element to fill its nearest positioned parent. NOVA's editor and welcome screen both use it so they can sit on top of each other.
  • position: fixed pins an element to the window (used for popup menus and toasts).
  • overflow: auto adds scrollbars only when needed.
  • z-index decides which overlapping element is on top. NOVA's modal overlay uses a high number so it covers the app.
WHAT IF IT WERE DIFFERENT? What if the sidebar had no min-height: 0?

This is a famous flexbox and grid trap. Flex and grid children refuse to shrink below their content size unless you say min-height: 0. Without it, a long file tree would make the sidebar taller than the window and the whole page would scroll instead of the tree. NOVA's CSS sets min-height: 0 on the workspace and panels for this reason.

7.10 Making it feel alive: transitions and animation

CSS
.chip { transition: background .12s; }
.chip:hover { background: var(--hover); }

@keyframes spin { to { transform: rotate(360deg); } }
#stBuild.busy::before { animation: spin .7s linear infinite; }
  • transition smooths a change over time (0.12 seconds is quick but visible).
  • @keyframes describes an animation. NOVA's little spinner in the status bar is a circle with one transparent side, rotated forever.
  • ::before and ::after are pseudo-elements: extra decoration that CSS can add without touching HTML.
WHY? Why are NOVA's animations so short?

Tools are used hundreds of times a day. A half-second fade is charming the first time and annoying the hundredth. Professional tools keep motion under about 150 milliseconds: enough to feel smooth, too short to wait for.

7.11 The cascade: who wins when rules clash?

If two rules set the same property on the same element, the browser picks the winner in this order:

  1. !important beats everything (use very rarely).
  2. More specific selectors beat less specific. An id (#sidebar) beats a class (.tab), which beats a tag (p).
  3. If still tied, the rule that comes later in the file wins.
WATCH OUT Watch out

Do not fight specificity with !important everywhere. NOVA uses it in only a handful of places, each for a good reason: forcing [hidden] to hide, letting the debugger line highlight and breakpoint dots beat Monaco's own styles, and keeping the terminal background transparent. If you need it twice in a row, rethink the selectors.

7.12 Media: dark and light, and print

CSS can read the user's preferences. For example, a page can follow the system theme:

CSS
@media (prefers-color-scheme: dark) {
  :root { --bg: #1e1f22; }
}

And it can prepare a page for printing. This very book is made from HTML and CSS: the black-and-white boxes, the 1.5 line spacing and the Times New Roman font come from a style sheet. For example:

CSS
body { font-family: 'Times New Roman', serif; font-size: 12pt; line-height: 1.5; }
.co-why { border-left: 7px solid #000; background: #f7f7f7; }

Chapter 8JavaScript: The Brain

8.1 What JavaScript is

JavaScript (JS) is the language that makes things happen. HTML says what is on the page and CSS says how it looks, but only JavaScript can say "when the user clicks Run, do this". Most of NOVA is JavaScript: about two thousand lines.

JavaScript began in 1995 as a quick scripting tool for web pages. Today it runs in browsers, on servers (Node.js), in desktop apps (Electron), on phones and even on tiny devices. It is one of the most used languages in the world.

KEY WORD Script

A script is a program that is run directly from its text by an interpreter or engine, without you producing a separate program file first.

8.2 Running JavaScript

There are two easy places to run it.

  1. The browser console. Press F12 in any browser, click Console, and type. Great for quick tests.
  2. Node.js. Save code in a file such as test.js and run node test.js in a terminal. All the runnable examples in this chapter work this way, and the outputs shown were produced by really running them while this book was made.

Your first program:

JavaScript
console.log("Hello, NOVA!");
console.log(2 + 3);
OUTPUT

console.log prints a value. It is your best friend for finding out what your program is doing.

8.3 Variables and types

A variable is a labelled box that holds a value. Use const for values that never change and let for values that will.

JavaScript
const name = "NOVA";        // text (a "string")
let version = 1;            // a number
const isFree = true;        // true or false (a "boolean")
const nothing = null;       // "on purpose, there is nothing"
let notSet;                 // undefined: "nobody gave me a value"

version = version + 1;      // allowed: let can change
console.log(name, version, isFree, nothing, notSet);
console.log(typeof name, typeof version, typeof isFree);

string number boolean
WHY? Why prefer const?

When you read const total = 5, you know instantly that total never changes, so you can stop worrying about it. Fewer things that can change means fewer places for a bug to hide. NOVA's code uses const almost everywhere and let only for things that must change, such as a counter.

WATCH OUT Watch out

Older JavaScript used var. It has confusing scope rules. You will see it in old code but should not write it in new code.

8.14 Time: the event loop, callbacks, promises and async/await

This is the hardest and most important part of JavaScript. Take it slowly.

One thing at a time

JavaScript can do only one thing at a time. Imagine a single waiter in a restaurant. If the waiter stood at the kitchen for ten minutes waiting for one soup, nobody else would be served. Instead the waiter drops the order at the kitchen and serves other tables. When the soup is ready, a bell rings.

In JavaScript the slow jobs (reading a file, waiting for a timer, a network request) are handed away. When they finish, their callback waits in a queue. The event loop checks over and over: "is the waiter free? Then serve the next callback."

JavaScript

console.log("2 end");
OUTPUT

2 end
3 promise
4 timer (even with 0 delay)

Study the output. Even a timer with zero delay waits until the current code has finished. Promises jump the queue and run before timers.

WHY? Why does this matter for an IDE?

If NOVA read a big file with a method that blocked the waiter, the whole window would freeze until the disk finished, and you could not click, type or scroll. Because every disk, process and message operation is asynchronous, the window always stays alive. This is the single biggest reason an Electron IDE feels smooth.

Debouncing: wait until the user stops

Every key you press changes the file, but you do not want to bother the language server after each letter. A debounce waits until typing pauses.

JavaScript
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);                       // cancel the earlier plan
    timer = setTimeout(() => fn(...args), ms); // make a new plan
  };
}
const send = debounce((text) => console.log("sent:", text), 120);

OUTPUT

Only one message is sent. This is the idea behind lspDidChange in NOVA, which waits 120 milliseconds.

WHY? Why does debounce use a closure?

The variable timer must survive between calls so that the next call can cancel the previous timer. The closure keeps it alive and private. This is a perfect, tiny example of why closures exist.

8.18 Worked project: a tiny interpreter

It is time to put the pieces together and build what Chapter 3 described: a lexer, a parser and an evaluator for sums such as 1 + 2 * 3. This runs in Node.

JavaScript
// 1. LEXER: text -> tokens
function tokenize(src) {
  const tokens = [];
  let i = 0;
  while (i < src.length) {
    const c = src[i];
    if (/\s/.test(c)) { i++; continue; }
    if (/[0-9.]/.test(c)) {
      let n = "";
      while (i < src.length && /[0-9.]/.test(src[i])) n += src[i++];
      tokens.push({ type: "num", value: parseFloat(n) });
      continue;
    }
    if ("+-*/()".includes(c)) { tokens.push({ type: c }); i++; continue; }
    throw new Error("Unexpected character: " + c);
  }
  return tokens;
}

// 2. PARSER: tokens -> tree
function parse(tokens) {
  let pos = 0;
  const peek = () => tokens[pos];
  const next = () => tokens[pos++];
  function expression() {                       // handles + and -
    let left = term();
    while (peek() && (peek().type === "+" || peek().type === "-")) {
      const op = next().type;
      left = { op, left, right: term() };
    }
    return left;
  }
  function term() {                             // handles * and /  (binds tighter)
    let left = factor();
    while (peek() && (peek().type === "*" || peek().type === "/")) {
      const op = next().type;
      left = { op, left, right: factor() };
    }
    return left;
  }
  function factor() {                           // numbers, (brackets), negatives
    const t = next();
    if (!t) throw new Error("Unexpected end");
    if (t.type === "num") return { num: t.value };
    if (t.type === "-") return { op: "neg", left: factor() };
    if (t.type === "(") {
      const e = expression();
      const close = next();
      if (!close || close.type !== ")") throw new Error("Missing )");
      return e;
    }
    throw new Error("Unexpected token " + t.type);
  }
  const tree = expression();
  if (pos < tokens.length) throw new Error("Extra input");
  return tree;
}

// 3. EVALUATOR: walk the tree
function evaluate(n) {
  if ("num" in n) return n.num;
  if (n.op === "neg") return -evaluate(n.left);
  const a = evaluate(n.left), b = evaluate(n.right);
  switch (n.op) {
    case "+": return a + b;
    case "-": return a - b;
    case "*": return a * b;
    case "/": return a / b;
  }
}

const run = (src) => evaluate(parse(tokenize(src)));
console.log(run("1 + 2 * 3"));
console.log(run("(1 + 2) * 3"));
console.log(run("10 / 4 - -2"));
console.log(JSON.stringify(parse(tokenize("1 + 2 * 3"))));
try { run("2 * (3 + "); } catch (e) { console.log("error:", e.message); }
OUTPUT
7
9
4.5
{"op":"+","left":{"num":1},"right":{"op":"*","left":{"num":2},"right":{"num":3}}}
error: Unexpected end
WHY? Why are there two functions, expression and term?

That is how the parser knows * happens before +. expression handles the low-priority operators and calls term for each piece. term handles the high-priority operators and calls factor. So 2 * 3 is gathered into one node before expression sees the plus sign. Each level of priority gets its own function. This technique is called recursive descent, and it is how many real compilers read code.

9.1 Why we need them

A normal web page is locked in a safe room called the sandbox. It cannot read your files, start programs or use your hard disk. That keeps you safe when you visit a website. But an IDE must read files, start compilers and talk to debuggers.

Two tools open the safe room, carefully:

WHY? Why does NOVA check buf.includes(0)?

9.3 Events: EventEmitter

Much of Node is built on events: "tell me when X happens".

WHY? Why events?

They let one part of a program announce something without knowing who cares. Adding a new listener never changes the saving code. This is how big programs stay flexible.

9.4 Starting other programs: child_process

This is the most important Node module for an IDE. It lets you start a program (the compiler, git, the debugger), feed it input and read its output.

JavaScript
const { spawn } = require("child_process");

// Start a child program: here we use Node itself as the "program".
const child = spawn(process.execPath, ["-e", "console.log('hello from child'); console.error('a warning'); process.exit(3)"]);

let out = "", err = "";
child.stdout.on("data", (chunk) => (out += chunk));
child.stderr.on("data", (chunk) => (err += chunk));
child.on("close", (code) => {
  console.log("stdout:", out.trim());
  console.log("stderr:", err.trim());
  console.log("exit code:", code);
});
OUTPUT
stdout: hello from child
stderr: a warning
exit code: 3

Every program has three standard streams:

Stream Name Used for
stdin standard input Text going into the program (keyboard or a pipe)
stdout standard output Normal text coming out
stderr standard error Error and warning text coming out

The exit code is a number the program returns when it ends: 0 means success, anything else means failure. NOVA prints it at the end of every run: "Process finished with exit code 0".

WHY? Why are stdout and stderr separate?

So you can treat them differently. NOVA draws stderr text in red. You can also save the normal output to a file and still see errors on the screen. Compilers print their error messages on stderr for exactly this reason.

Output arrives in chunks

JavaScript
const { spawn } = require("child_process");
const script = "let n=0; const t=setInterval(()=>{ process.stdout.write('part '+(++n)+'\\n'); if(n==3){clearInterval(t)} }, 50)";
const child = spawn(process.execPath, ["-e", script]);
let chunks = 0;
child.stdout.on("data", (c) => { chunks++; console.log("received:", c.toString().trim()); });
child.on("close", () => console.log("chunks:", chunks));
OUTPUT
received: part 1
received: part 2
received: part 3
chunks: 3

Data does not arrive as neat whole lines. A line may be split across two chunks, or two lines can arrive in one chunk. This is why NOVA keeps a buffer and only parses complete lines (see execStep in app.js).

WHAT IF IT WERE DIFFERENT? What if you parse each chunk as if it were a line?

Sometimes a compiler error such as main.cpp:14:9: error: 'x' was not declared arrives split into main.cpp:14:9: err and or: 'x' was not declared. The pattern would match neither piece, and the error would silently vanish. Buffering until the newline is the cure.

Worked example: a tiny process runner

NOVA wraps spawn in a helper so the rest of the code can simply await the result. Here is the same idea:

JavaScript
const { spawn } = require("child_process");

function runCommand(cmd, args, input) {
  return new Promise((resolve) => {
    const child = spawn(cmd, args);
    let stdout = "", stderr = "";
    child.stdout.on("data", d => (stdout += d));
    child.stderr.on("data", d => (stderr += d));
    child.on("error", (e) => resolve({ code: -1, stdout, stderr: stderr + e.message }));
    child.on("close", (code) => resolve({ code, stdout, stderr }));
    if (input !== undefined) { child.stdin.write(input); child.stdin.end(); }
  });
}

async function main() {
  const r1 = await runCommand(process.execPath, ["-e", "console.log(1 + 1)"]);
  console.log(r1.code, JSON.stringify(r1.stdout));

  const r2 = await runCommand(process.execPath, ["-e", "process.stdin.on('data', d => console.log(d.toString().toUpperCase()))"], "shout this");
  console.log(r2.code, JSON.stringify(r2.stdout.trim()));

  const r3 = await runCommand("no-such-program-xyz", []);
  console.log(r3.code, r3.stderr.includes("ENOENT"));
}
main();
OUTPUT
0 "2\n"
0 "SHOUT THIS"
-1 true

Study r3. Starting a program that does not exist does not crash Node; it fires an 'error' event. NOVA handles it by printing "Failed to start" in the Run panel. If the 'error' handler were missing, Node would throw an uncaught exception and the whole IDE would crash.

WATCH OUT Watch out

Always handle the 'error' event on a child process. It is the most common cause of mysterious crashes in tools that start other programs.

9.6 The safe bridge: preload and contextBridge

Now the most important security idea in Electron.

JavaScript
// main.js
webPreferences: { preload: path.join(__dirname, 'preload.js'), contextIsolation: true, nodeIntegration: false }
  • nodeIntegration: false means the web page cannot use require, fs or child_process.
  • contextIsolation: true means the preload script runs in a separate world from the page, so the page cannot tamper with it.

The preload script is allowed to use Electron's APIs, and it hands the page only a small, named set of functions:

JavaScript
// preload.js
const { contextBridge, ipcRenderer } = require('electron');
const inv = (ch) => (...a) => ipcRenderer.invoke(ch, ...a);
contextBridge.exposeInMainWorld('nova', {
  read: inv('fs:read'),
  write: inv('fs:write'),
  readDir: inv('fs:readDir'),
  start: inv('proc:start'),
  kill: inv('proc:kill'),
  onData: (cb) => ipcRenderer.on('proc:data', (_e, m) => cb(m)),
});

After this, any script in the window can call window.nova.read(path) and nothing else from Node. The helper inv is a closure factory: it turns the channel name into a function that forwards its arguments.

WHAT IF IT WERE DIFFERENT? What if nodeIntegration were true?

A script in your page could write require('child_process').exec('del /s /q C:\\*'). If your IDE ever displayed one malicious string as HTML (for example a hostile file name or compiler message), your computer could be wiped. With the bridge, the worst a page can do is call the few functions you chose to expose, and each can be written to check its arguments.

invoke and handle: asking and answering

The main process registers handlers for channel names:

JavaScript
// main.js
ipcMain.handle('fs:readDir', async (_e, dir) => {
  const ents = await fs.promises.readdir(dir, { withFileTypes: true });
  return ents
    .filter(d => !IGNORE.has(d.name))
    .map(d => ({ name: d.name, path: path.join(dir, d.name), dir: d.isDirectory() }))
    .sort((a, b) => (b.dir - a.dir) || a.name.localeCompare(b.name));
});

The window then writes const files = await nova.readDir(folder). The reply is whatever the handler returns, delivered through a promise.

WHY? Why sort inside the main process?

The sort puts folders before files and then orders alphabetically, ignoring capital letters. (b.dir - a.dir) uses a trick: true - false is 1, so directories rise to the top. Doing it once, in the engine room, means every part of the window gets a tidy list for free.

Pushing messages: send

Some information flows the other way, not as an answer but as news: a program has printed a line. The main process pushes it:

JavaScript
// main.js
child.stdout.on('data', d =>
  win.webContents.send('proc:data', { id, stream: 'out', data: d.toString() }));

and the bridge forwards it to a listener the window registered with nova.onData(callback).

Worked example: a mini IPC bus you can run

You cannot run Electron's IPC outside Electron, but you can build the idea with a few lines and see why invoke and handle feel like function calls:

JavaScript
const handlers = new Map();
const ipcMain = { handle: (ch, fn) => handlers.set(ch, fn) };
const ipcRenderer = { invoke: async (ch, ...args) => {
  const fn = handlers.get(ch);
  if (!fn) throw new Error("No handler for " + ch);
  return fn({}, ...args);
} };

// "main process" side
ipcMain.handle("math:add", async (_e, a, b) => a + b);
ipcMain.handle("fs:fakeRead", async (_e, name) => ({ text: "contents of " + name }));

// "window" side
(async () => {
  console.log(await ipcRenderer.invoke("math:add", 20, 22));
  console.log(await ipcRenderer.invoke("fs:fakeRead", "main.cpp"));
  try { await ipcRenderer.invoke("nope"); } catch (e) { console.log("error:", e.message); }
})();
OUTPUT
42
{ text: 'contents of main.cpp' }
error: No handler for nope

The real thing also copies your arguments between processes (so the two sides never share memory), but the shape is identical.

Chapter 10C: The Foundation

10.1 Why learn C?

C was created in 1972 and is still everywhere: operating systems, phones, game engines, car engines, and even the compilers and debuggers that NOVA drives. C is small. You can learn all of it. And it shows you what the computer is really doing, which makes you better at every other language.

C gives you great power and few safety nets. It trusts you. That is why it is fast, and why mistakes can be nasty. In this chapter you will learn both the power and the discipline.

IN PLAIN WORDS In plain words

Most languages are like driving an automatic car: comfortable, but you do not see the gears. C is a manual car with no seat-belt warning. You feel everything, and you learn how engines work.

10.2 Setting up

You need a compiler. NOVA uses gcc (the C compiler of the GNU project). Check it is installed:

gcc --version

Save code in a file ending in .c (for example hello.c) and build it:

gcc hello.c -o hello.exe
hello.exe

Or open the file in NOVA and press the green Run button. NOVA runs exactly the same commands for you (with extra options -g -Wall -Wextra: -g adds debugging information, -Wall -Wextra turn on helpful warnings).

10.3 Hello, world

C
#include <stdio.h>

int main(void) {
    printf("Hello, NOVA!\n");
    return 0;
}
OUTPUT
Hello, NOVA!

Line by line:

  • #include <stdio.h> pastes in the description of the standard input/output functions, including printf. Without it the compiler would not know what printf is.
  • int main(void) is where every C program starts. int says that it gives back a whole number when it ends.
  • { } hold the body of the function.
  • printf("...") prints text. \n is a newline character (it moves to the next line).
  • return 0; ends the program and says "success".
  • Every statement ends with a semicolon ;.
WHY? Why does main return 0?

The number is the program's exit code, which the operating system and tools such as NOVA read. By agreement 0 means success and anything else means failure. NOVA prints it after every run: "Process finished with exit code 0". Build scripts rely on it: if your program returns non-zero, the build stops.

WHAT IF IT WERE DIFFERENT? What if you forget the semicolon or the #include?

The compiler stops with an error such as expected ';' before 'return' or a warning like implicit declaration of function 'printf'. These appear as red and yellow wavy lines in NOVA. Reading these messages carefully is a core skill: the line number is where the compiler noticed the problem, which is sometimes one line after where you made it.

10.4 Variables and types

C
#include <stdio.h>

int main(void) {
    int age = 25;               // whole number
    double price = 19.99;       // number with decimals
    char letter = 'N';          // one character (note the single quotes)
    const int days = 7;         // cannot change

    printf("age=%d price=%.2f letter=%c days=%d\n", age, price, letter, days);
    printf("sizes: int=%zu double=%zu char=%zu\n", sizeof(int), sizeof(double), sizeof(char));
    age = age + 1;
    printf("next year: %d\n", age);
    return 0;
}
OUTPUT
age=25 price=19.99 letter=N days=7
sizes: int=4 double=8 char=1
next year: 26

The pieces %d, %.2f, %c, %zu are format specifiers: placeholders that printf fills from the values that follow.

Specifier Prints Example
%d whole number (int) 42
%u unsigned whole number 42
%f %.2f decimal number (2 decimals) 3.14
%c one character A
%s text (string) hello
%x hexadecimal ff
%p a pointer (address) 0x7ffd...
%zu size values (sizeof) 8
WHY? Why do types exist?

A variable is just a place in memory. The type tells the compiler how many bytes to set aside and how to read them. The same four bytes can mean the number 1078530011 or the decimal 3.14159. Without the type the computer would not know which. (Python and JavaScript decide types at run time. C decides at compile time, which is faster and catches mistakes earlier.)

Sizes matter

A byte is 8 bits. On most computers: char is 1 byte, int is 4 bytes, long long is 8, double is 8, and a pointer is 8 on a 64-bit system. An int holds roughly minus two billion to plus two billion. Go past it and the number wraps around:

C
#include <stdio.h>
#include <limits.h>

int main(void) {
    printf("INT_MAX = %d\n", INT_MAX);
    unsigned int big = 4000000000u;
    printf("unsigned big = %u\n", big);
    unsigned char small = 250;
    small = small + 10;                 // 260 does not fit in one byte
    printf("small after +10 = %d\n", small);
    return 0;
}
OUTPUT
INT_MAX = 2147483647
unsigned big = 4000000000
small after +10 = 4
WATCH OUT Watch out

Overflowing a signed int is undefined behaviour in C: the compiler is allowed to do anything. Unsigned overflow is defined (it wraps). Many famous security bugs come from number overflow.

10.5 Deciding and repeating

C
#include <stdio.h>

int main(void) {
    int score = 72;
    if (score >= 90) printf("A\n");
    else if (score >= 70) printf("B\n");
    else printf("C or below\n");

    for (int i = 1; i <= 5; i++) printf("%d ", i * i);
    printf("\n");

    int n = 10, steps = 0;
    while (n != 1) {                       // the Collatz puzzle
        n = (n % 2 == 0) ? n / 2 : 3 * n + 1;
        steps++;
    }
    printf("steps to reach 1: %d\n", steps);

    switch (score / 10) {
        case 10: case 9: printf("excellent\n"); break;
        case 7: printf("good\n"); break;
        default: printf("keep going\n");
    }
    return 0;
}
OUTPUT
B
1 4 9 16 25 
steps to reach 1: 6
good
WHAT IF IT WERE DIFFERENT? What if you forget break in a switch?

Execution "falls through" into the next case and runs its code too. Sometimes that is done on purpose (as with case 10: case 9: above) but forgetting break is a classic bug. Modern compilers warn about it with -Wextra, which is one reason NOVA always passes that option.

10.6 Functions

C
#include <stdio.h>

int square(int x);                  // prototype: promise that this function exists

int main(void) {
    printf("%d %d\n", square(7), square(square(2)));
    return 0;
}

int square(int x) {                 // definition
    return x * x;
}
OUTPUT
49 16

A prototype tells the compiler the function's name, input types and output type before it is defined, so you can call it earlier in the file. Prototypes for a whole set of functions go in a header file (.h), as you will see in the multi-file section.

WHY? Why does C copy arguments?

C passes arguments by value: the function receives a copy. Changing the copy never changes the original. That is safe and predictable. When you do want the function to change the caller's variable, you pass its address (a pointer), which is the next big topic.

10.7 Arrays and strings

An array is a row of items of the same type, side by side in memory.

C
#include <stdio.h>

int main(void) {
    int a[5] = {10, 20, 30, 40, 50};
    int sum = 0;
    for (int i = 0; i < 5; i++) sum += a[i];
    printf("sum=%d average=%.1f\n", sum, sum / 5.0);
    printf("bytes in a: %zu, items: %zu\n", sizeof a, sizeof a / sizeof a[0]);
    return 0;
}
OUTPUT
sum=150 average=30.0
bytes in a: 20, items: 5
WHAT IF IT WERE DIFFERENT? What if you read a[5] or a[-1]?

C does not check array bounds. You will read (or overwrite) whatever happens to sit next to the array. The program may print garbage, crash, or seem fine until the worst moment. This is called undefined behaviour and is the root of countless security holes. Always make sure your index is between 0 and size minus 1.

Strings are character arrays

C has no string type. A string is an array of char that ends with a special zero character '\0', the null terminator.

C
#include <stdio.h>
#include <string.h>
#include <ctype.h>

int main(void) {
    char name[] = "NOVA";                     // 5 bytes: N O V A \0
    printf("%s has length %zu but takes %zu bytes\n", name, strlen(name), sizeof name);

    char copy[20];
    strcpy(copy, name);
    strcat(copy, " IDE");
    printf("%s\n", copy);
    printf("%d %d\n", strcmp("apple", "banana") < 0, strcmp("same", "same"));

    for (int i = 0; copy[i] != '\0'; i++) copy[i] = (char)toupper((unsigned char)copy[i]);
    printf("%s\n", copy);

    char text[] = "one two three";
    for (char *tok = strtok(text, " "); tok; tok = strtok(NULL, " ")) printf("[%s]", tok);
    printf("\n");
    return 0;
}
OUTPUT
NOVA has length 4 but takes 5 bytes
NOVA IDE
1 0
NOVA IDE
[one][two][three]
WHY? Why the null terminator?

The string functions need to know where a string ends, but an array does not carry its own length. So the convention is: the string ends at the first zero. strlen simply counts until it finds one. The price is danger: if the zero is missing, the functions run on into memory that is not yours.

WATCH OUT Watch out

strcpy and strcat do not check that the destination is big enough. Copying a long string into a short buffer is a buffer overflow. Prefer snprintf(buf, sizeof buf, ...), which cuts the output to fit.

10.8 Pointers: the big idea

Every variable lives at an address in memory. A pointer is a variable that holds an address.

C
#include <stdio.h>

int main(void) {
    int age = 25;
    int *p = &age;                 // & = "address of"
    printf("age=%d, *p=%d\n", age, *p);   // * = "the thing p points to"
    *p = 30;                       // change age THROUGH the pointer
    printf("age is now %d\n", age);
    printf("same address? %d\n", p == &age);
    return 0;
}
OUTPUT
age=25, *p=25
age is now 30
same address? 1

Why bother? Because with a pointer a function can change the caller's variable:

C
#include <stdio.h>

void swap(int *a, int *b) {
    int tmp = *a;
    *a = *b;
    *b = tmp;
}

int main(void) {
    int x = 1, y = 2;
    swap(&x, &y);
    printf("x=%d y=%d\n", x, y);
    return 0;
}
OUTPUT
x=2 y=1

Pointers and arrays are cousins

The name of an array can be used as a pointer to its first item. Adding 1 to a pointer moves it by one item, not one byte.

C
#include <stdio.h>

int main(void) {
    int a[4] = {10, 20, 30, 40};
    int *p = a;
    printf("%d %d %d\n", *p, *(p + 2), p[3]);
    for (int *q = a; q < a + 4; q++) printf("%d ", *q);
    printf("\n");
    printf("distance in items: %td\n", (a + 3) - a);
    return 0;
}
OUTPUT
10 30 40
10 20 30 40 
distance in items: 3
WHAT IF IT WERE DIFFERENT? What if a pointer points at nothing?

A pointer you have not set holds random garbage. Using it (dereferencing) usually crashes the program with a "segmentation fault". A pointer that deliberately points nowhere is set to NULL. Always check if (p != NULL) before using a pointer that might be empty. In NOVA's debugger you can see a pointer's value in the Variables panel.

10.9 Memory: the stack and the heap

Your program has regions of memory with different jobs.

  • The stack holds local variables and function calls. It is automatic: variables appear when a function starts and vanish when it ends. It is fast but limited in size.
  • The heap is a big pool you borrow from with malloc and give back with free. It lasts until you free it, and its size is limited only by your computer.
C
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int n = 5;
    int *data = malloc(n * sizeof *data);        // borrow room for 5 ints
    if (data == NULL) { printf("out of memory\n"); return 1; }

    for (int i = 0; i < n; i++) data[i] = (i + 1) * 100;

    data = realloc(data, 8 * sizeof *data);       // grow to 8 ints
    for (int i = 5; i < 8; i++) data[i] = 0;
    for (int i = 0; i < 8; i++) printf("%d ", data[i]);
    printf("\n");

    free(data);                                   // give it back
    data = NULL;                                  // so we cannot use it by accident
    return 0;
}
OUTPUT
100 200 300 400 500 0 0 0
WHY? Why do we write malloc(n * sizeof *data) and not malloc(20)?

sizeof *data means "the size of whatever data points to". If you later change int to double, the size follows automatically. A hard-coded 20 would silently become wrong. Writing code that adapts is a mark of a careful programmer.

The three famous heap mistakes:

Mistake Name Result
Forgetting free Memory leak The program slowly eats memory
Using memory after free Dangling pointer / use-after-free Garbage or a crash, sometimes a security hole
Calling free twice on the same pointer Double free A crash

Setting the pointer to NULL after free makes the second and third mistakes much easier to catch.

10.10 Structs, enums and typedef

A struct groups different pieces of data under one name.

C
#include <stdio.h>
#include <string.h>

typedef enum { RED, GREEN, BLUE } Color;

typedef struct {
    char name[20];
    int x, y;
    Color color;
} Point;

void show(const Point *p) {                  // const: this function promises not to change it
    static const char *names[] = {"red", "green", "blue"};
    printf("%s at (%d,%d) is %s\n", p->name, p->x, p->y, names[p->color]);
}

int main(void) {
    Point a = { "origin", 0, 0, RED };
    Point b;
    strcpy(b.name, "far");
    b.x = 10; b.y = 20; b.color = BLUE;
    show(&a);
    show(&b);
    printf("sizeof(Point) = %zu\n", sizeof(Point));
    return 0;
}
OUTPUT
origin at (0,0) is red
far at (10,20) is blue
sizeof(Point) = 32
  • p->x is a shortcut for (*p).x: "the x of the thing p points to".
  • enum gives names to small numbers (RED is 0, GREEN is 1, ...).
  • typedef lets you say Point instead of struct Point.

Why is the struct bigger than its parts?

C
#include <stdio.h>

struct Bad  { char a; int b; char c; };     // padding between and after
struct Good { int b; char a; char c; };     // same fields, smaller

int main(void) {
    printf("Bad  = %zu bytes\n", sizeof(struct Bad));
    printf("Good = %zu bytes\n", sizeof(struct Good));
    return 0;
}
OUTPUT
Bad  = 12 bytes
Good = 8 bytes
WHY? Why does the order of fields change the size?

CPUs read memory fastest when a 4-byte number starts at an address divisible by 4. The compiler adds padding bytes to guarantee it. Putting large fields first and small ones together wastes less. In an IDE that stores millions of tiny objects (such as syntax tokens) this saving is real.

10.11 Reading and writing files

C
#include <stdio.h>

int main(void) {
    FILE *f = fopen("notes.txt", "w");
    if (!f) { perror("open for writing"); return 1; }
    fprintf(f, "line one\nline two\nline three\n");
    fclose(f);

    f = fopen("notes.txt", "r");
    if (!f) { perror("open for reading"); return 1; }
    char line[100];
    int count = 0;
    while (fgets(line, sizeof line, f)) {
        count++;
        printf("%d: %s", count, line);
    }
    fclose(f);

    f = fopen("does-not-exist.txt", "r");
    if (!f) printf("could not open: file missing\n");
    remove("notes.txt");
    return 0;

OUTPUT
1: line one
2: line two
3: line three
could not open: file missing
WHY? Why check whether fopen returned NULL?

Files can be missing, locked or unreadable. fopen signals failure by returning NULL. If you use that NULL as a file, the program crashes. Checking every operation that can fail is how professional C code stays reliable. perror prints a helpful reason.

10.12 Function pointers and callbacks

A function also lives at an address, so you can store it and pass it around. The standard library's qsort sorts anything because you give it a function that compares two items.

C
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct { const char *name; int lines; } File;

static int by_lines(const void *a, const void *b) {
    const File *x = a, *y = b;
    return (x->lines > y->lines) - (x->lines < y->lines);
}
static int by_name(const void *a, const void *b) {
    return strcmp(((const File *)a)->name, ((const File *)b)->name);
}

int main(void) {
    File files[] = { {"main.c", 120}, {"util.c", 45}, {"app.c", 300} };
    size_t n = sizeof files / sizeof files[0];

    qsort(files, n, sizeof files[0], by_lines);
    for (size_t i = 0; i < n; i++) printf("%s(%d) ", files[i].name, files[i].lines);
    printf("\n");

    qsort(files, n, sizeof files[0], by_name);
    for (size_t i = 0; i < n; i++) printf("%s(%d) ", files[i].name, files[i].lines);
    printf("\n");
    return 0;
}
OUTPUT
util.c(45) main.c(120) app.c(300) 
app.c(300) main.c(120) util.c(45)

10.14 Many files: headers and linking

A real project splits into files. The header (.h) lists what exists; the source (.c) holds how it works.

C

#define MATHUTIL_H

#endif

10.15 Putting it together: a growable list

Real programs need arrays that grow. C has none built in, so we build one: a structure holding a pointer, a count and a capacity. This is the pattern behind C++'s std::vector.

C
#include <stdio.h>
#include <stdlib.h>

typedef struct {
    int *items;
    size_t count, capacity;
} IntList;

void list_init(IntList *l) { l->items = NULL; l->count = 0; l->capacity = 0; }

int list_push(IntList *l, int value) {
    if (l->count == l->capacity) {
        size_t cap = l->capacity ? l->capacity * 2 : 2;
        int *bigger = realloc(l->items, cap * sizeof *bigger);
        if (!bigger) return 0;                 // old memory is still valid
        l->items = bigger;
        l->capacity = cap;
    }
    l->items[l->count++] = value;
    return 1;
}

void list_free(IntList *l) { free(l->items); list_init(l); }

int main(void) {
    IntList list;
    list_init(&list);
    for (int i = 1; i <= 10; i++) {
        list_push(&list, i * i);
        printf("count=%zu capacity=%zu\n", list.count, list.capacity);
    }
    for (size_t i = 0; i < list.count; i++) printf("%d ", list.items[i]);
    printf("\n");
    list_free(&list);
    return 0;
}
OUTPUT
count=1 capacity=2
count=2 capacity=2
count=3 capacity=4
count=4 capacity=4
count=5 capacity=8
count=6 capacity=8
count=7 capacity=8
count=8 capacity=8
count=9 capacity=16
count=10 capacity=16
1 4 9 16 25 36 49 64 81 100
WHY? Why double the capacity instead of adding one?

If you grew by one each time, ten thousand pushes would copy the data about fifty million times in total. Doubling means each item is copied only a few times on average, so pushing is fast ("amortised constant time"). This single idea is why std::vector and JavaScript arrays are fast.

WHAT IF IT WERE DIFFERENT? What if you wrote l->items = realloc(l->items, ...) directly?

If realloc fails it returns NULL, and you would overwrite your only pointer to the old memory with NULL, leaking it and crashing later. That is why the code stores the result in bigger first and checks it. Small details like this separate careful C from risky C.

A linked list

Another classic structure: items scattered in memory, each pointing to the next.

C
#include <stdio.h>
#include <stdlib.h>

typedef struct Node {
    int value;
    struct Node *next;
} Node;

Node *push_front(Node *head, int v) {
    Node *n = malloc(sizeof *n);
    n->value = v;
    n->next = head;
    return n;
}

void print_list(const Node *n) {
    for (; n; n = n->next) printf("%d -> ", n->value);
    printf("NULL\n");
}

Node *reverse(Node *head) {
    Node *prev = NULL;
    while (head) {
        Node *next = head->next;
        head->next = prev;
        prev = head;
        head = next;
    }
    return prev;
}

void free_list(Node *n) {
    while (n) { Node *next = n->next; free(n); n = next; }
}

int main(void) {
    Node *list = NULL;
    for (int i = 1; i <= 4; i++) list = push_front(list, i);
    print_list(list);
    list = reverse(list);
    print_list(list);
    free_list(list);
    return 0;
}
OUTPUT
4 -> 3 -> 2 -> 1 -> NULL
1 -> 2 -> 3 -> 4 -> NULL

10.16 Bits and bytes

C
#include <stdio.h>

int main(void) {
    unsigned flags = 0;
    enum { BOLD = 1u << 0, ITALIC = 1u << 1, UNDERLINE = 1u << 2 };

    flags |= BOLD | UNDERLINE;          // turn bits ON
    flags &= ~UNDERLINE;                // turn a bit OFF
    flags ^= ITALIC;                    // flip a bit
    printf("flags=%u bold=%d italic=%d underline=%d\n", flags,
           (flags & BOLD) != 0, (flags & ITALIC) != 0, (flags & UNDERLINE) != 0);
    printf("0x%02X %d %d\n", 255, 5 >> 1, 5 << 2);

}
OUTPUT

0xFF 2 20

Bit flags let one number carry many yes/no settings in a single byte. File permissions, window styles and network headers all use them.

QUIZ
  1. What does return 0; from main mean?
  2. Why must a string end with '\0'?
  3. What do &x and *p mean?
  4. Why does swap(int a, int b) fail to swap, but swap(int *a, int *b) works?
  5. What is the difference between the stack and the heap?
  6. Name the three common heap mistakes.
  7. Why might sizeof(struct Bad) be larger than the sum of its fields?
  8. What is wrong with #define SQUARE(x) x * x?
  9. What do include guards prevent?
  10. What does the linker do and what error appears if it cannot find a function?
  11. Why double a growable array's capacity instead of adding one?
  12. Why store the result of realloc in a new variable first?
ANSWERS
  1. The program succeeded (exit code 0).
  2. The string functions find the end by looking for the zero; without it they read past the end.
  3. &x is the address of x; *p is the value stored at the address p holds.
  4. C passes copies. Swapping copies changes nothing. Passing addresses lets the function change the caller's variables.
  5. The stack is automatic, fast and limited (local variables); the heap is large and manual (malloc/free).
  6. Memory leak, use after free (dangling pointer), double free.
  7. The compiler inserts padding so fields start at addresses the CPU prefers.
  8. Missing brackets: SQUARE(3 + 1) becomes 3 + 1 * 3 + 1. It must be ((x) * (x)).
  9. A header being included twice and its contents being defined twice.
  10. It joins object files and libraries into one program. "undefined reference to ..." appears.
  11. Doubling copies each element only a few times on average, so pushing is fast.
  12. If realloc fails it returns NULL, and assigning that straight back would lose the only pointer to the old memory (a leak).

11.1 What C++ adds

C++ began as "C with classes" in 1979 and has grown into a huge language. 11.2 Hello, C++

C++

11.3 Everyday tools

References: a nickname for a variable

C++
#include <iostream>

void addOne(int& n) { n += 1; }               // & means: work on the ORIGINAL
void show(const int& n) { std::cout << n << '\n'; }   // const&: read-only, no copy

int main() {
    int x = 5;
    addOne(x);
    int& alias = x;                           // alias is another name for x
    alias = 100;
    show(x);
    return 0;
}
OUTPUT
100

A reference is a pointer wearing a friendlier face: it is automatically dereferenced and can never be null. Use const T& to pass big things (such as strings) without copying them.

auto and range-for

C++
#include <iostream>
#include <vector>
#include <string>

int main() {
    std::vector<std::string> parts = {"editor", "tree", "terminal"};
    for (const auto& p : parts) std::cout << p << ' ' << p.size() << '\n';
    auto total = 0;
    for (auto& p : parts) { p += "!"; total += static_cast<int>(p.size()); }
    std::cout << parts.back() << ' ' << total << '\n';
    return 0;
}
OUTPUT
editor 6
tree 4
terminal 8
terminal! 21
  • auto lets the compiler work out the type.
  • for (const auto& p : parts) visits every element. With & there is no copy; with const you promise not to change it. NOVA's sample project uses exactly this loop to add up circle areas.

Strings

std::string replaces C's fragile character arrays. It grows by itself and knows its own length.

C++
#include <iostream>
#include <string>

int main() {
    std::string s = "NOVA";
    s += " IDE";
    std::cout << s << ' ' << s.size() << ' ' << s.substr(0, 4) << '\n';
    std::cout << (s.find("IDE") != std::string::npos) << ' ' << s.find('V') << '\n';
    s.replace(0, 4, "Nova");
    std::cout << s << ' ' << (s == "Nova IDE") << ' ' << std::to_string(42) + "!" << '\n';
    std::cout << std::stoi("123") + 1 << '\n';
    return 0;
}
OUTPUT
NOVA IDE 8 NOVA
1 2
Nova IDE 1 42!
124
WHY? Why is std::string safer than char arrays?

There is no null terminator to forget and no buffer to overflow: when you append, the string allocates more memory itself. The whole class of bugs warned about in Chapter 10 mostly vanishes. It is a perfect example of C++'s motto: make the safe thing the easy thing.

11.5 Classes: your own types

A class bundles data (member variables) with the functions that work on it (member functions). It is the most important feature of C++. This is the very class from NOVA's sample project, now complete.

C++
#include <iostream>

class Circle {
public:
    explicit Circle(double r) : radius_(r) {}          // constructor
    double area() const { return 3.14159265 * radius_ * radius_; }
    void grow(double by) { radius_ += by; }
    double radius() const { return radius_; }

private:
    double radius_;                                    // hidden from outside
};

int main() {
    Circle c(2.0);
    std::cout << c.area() << '\n';
    c.grow(1.0);
    std::cout << c.radius() << ' ' << c.area() << '\n';
    // c.radius_ = -5;      // ERROR: radius_ is private
    return 0;
}
OUTPUT
12.5664
3 28.2743

Reading it:

  • public: members can be used by anyone; private: members only by the class itself.
  • The constructor Circle(double r) runs when an object is created. : radius_(r) is the initializer list: it sets the member directly.
  • const after area() is a promise: this function will not change the object. A const Circle can only call const functions.
  • explicit stops accidental conversions such as Circle c = 5;.
WHY? Why make radius_ private?

So nobody can set it to an impossible value like -5 behind the class's back. If the only way to change the radius is through grow, then grow can check the rules. This is encapsulation: the class guards its own data. Later, if you store the radius differently, no outside code needs to change.

WHAT IF IT WERE DIFFERENT? What if area() were not marked const?

Then you could not call it on a const Circle&, which is what you get when you write for (const auto& c : circles). The compiler would refuse with an error about discarding qualifiers. Marking everything that does not modify state as const is a habit worth forming from day one.

11.6 RAII: the idea that defines C++

RAII stands for Resource Acquisition Is Initialization. It is a clumsy name for a simple, powerful idea: tie the life of a resource (a file, memory, a lock) to the life of an object. The constructor takes the resource and the destructor gives it back.

C++
#include <cstdio>
#include <iostream>
#include <stdexcept>

class File {
public:
    File(const char* path, const char* mode) : f_(std::fopen(path, mode)) {
        if (!f_) throw std::runtime_error("cannot open file");
    }
    ~File() { if (f_) { std::fclose(f_); std::cout << "[file closed]\n"; } }
    File(const File&) = delete;                  // forbid copying (two owners would double-close)
    File& operator=(const File&) = delete;
    void write(const char* text) { std::fputs(text, f_); }
private:
    std::FILE* f_;
};

int main() {
    try {
        File f("raii_demo.txt", "w");
        f.write("hello\n");
        throw std::runtime_error("something went wrong halfway");
    } catch (const std::exception& e) {
        std::cout << "caught: " << e.what() << '\n';
    }
    std::remove("raii_demo.txt");
    return 0;
}
OUTPUT
[file closed]
caught: something went wrong halfway

Notice that although an error was thrown, the line [file closed] is printed: the destructor still ran, because leaving the block, even by exception, destroys its objects.

WHAT IF IT WERE DIFFERENT? What if you used fopen and fclose by hand?

You would need an fclose on every possible path out of the function: normal return, early return, and every exception. Forget one and you leak the file handle. In big programs this is unmanageable. RAII reduces it to nothing to remember.

Smart pointers

Raw new and delete are RAII's enemy: forgetting delete leaks. Smart pointers wrap them in objects that delete automatically.

C++
#include <iostream>
#include <memory>
#include <vector>

struct Tab {
    explicit Tab(int id) : id(id) { std::cout << "open tab " << id << '\n'; }
    ~Tab() { std::cout << "close tab " << id << '\n'; }
    int id;
};

int main() {
    auto a = std::make_unique<Tab>(1);          // exactly ONE owner
    std::cout << a->id << '\n';
    auto b = std::move(a);                      // ownership moves; a is now empty
    std::cout << (a == nullptr) << ' ' << b->id << '\n';

    auto s1 = std::make_shared<Tab>(2);         // SHARED ownership, counted
    {
        auto s2 = s1;
        std::cout << "owners: " << s1.use_count() << '\n';
    }
    std::cout << "owners: " << s1.use_count() << '\n';

    std::vector<std::unique_ptr<Tab>> tabs;
    tabs.push_back(std::make_unique<Tab>(3));
    std::cout << "leaving main\n";
    return 0;
}

Type Meaning Use it when
std::unique_ptr<T> One owner, deleted when it goes away Default choice
std::shared_ptr<T> Many owners, deleted when the last one goes away You truly need shared ownership

WHY? Why is unique_ptr the default?

Single ownership is simple to reason about: the owner decides when the object dies. shared_ptr costs a counter and makes lifetimes harder to see. Modern C++ code almost never contains a bare new or delete.

11.7 Inheritance and polymorphism

A class can inherit from another: it gets all its members and adds more. With virtual functions a base-class pointer can run the right version for the real object. This is polymorphism.

C++
#include <iostream>
#include <memory>
#include <vector>
#include <cmath>

class Shape {
public:
    virtual ~Shape() = default;                 // always make base destructors virtual
    virtual double area() const = 0;            // "= 0": pure virtual, must be overridden
    virtual const char* name() const = 0;
};

class Circle : public Shape {
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.14159265 * r_ * r_; }
    const char* name() const override { return "circle"; }
private:
    double r_;
};

class Rect : public Shape {
public:
    Rect(double w, double h) : w_(w), h_(h) {}
    double area() const override { return w_ * h_; }
    const char* name() const override { return "rectangle"; }
private:
    double w_, h_;
};

int main() {
    std::vector<std::unique_ptr<Shape>> shapes;
    shapes.push_back(std::make_unique<Circle>(1.0));
    shapes.push_back(std::make_unique<Rect>(3.0, 4.0));
    shapes.push_back(std::make_unique<Circle>(2.0));

    double total = 0;
    for (const auto& s : shapes) {
        std::cout << s->name() << ": " << s->area() << '\n';
        total += s->area();
    }
    std::cout << "total: " << total << '\n';
    return 0;
}
OUTPUT
circle: 3.14159
rectangle: 12
circle: 12.5664
total: 27.708
WHY? Why virtual ~Shape()?

When a unique_ptr<Shape> deletes a Circle through a Shape pointer, only a virtual destructor makes C++ run the Circle destructor. Without it the Circle part is never cleaned up properly: undefined behaviour. Rule: a class meant to be a base needs a virtual destructor.

WHAT IF IT WERE DIFFERENT? What if you write override and misspell the name?

override tells the compiler "this must replace a base function". If you write aera() or change a const, the compiler stops with an error. Without override you would silently create a new function and the base one would never be replaced. It is a tiny keyword that prevents a very sneaky bug.

11.9 Templates: code for any type

A template is a recipe the compiler uses to write code for each type you need.

C++
#include <iostream>
#include <string>
#include <vector>

template <typename T>
T biggest(const T& a, const T& b) { return a < b ? b : a; }

template <typename T>
class Stack {
public:
    void push(const T& v) { items_.push_back(v); }
    T pop() { T v = items_.back(); items_.pop_back(); return v; }
    bool empty() const { return items_.empty(); }
    size_t size() const { return items_.size(); }
private:
    std::vector<T> items_;
};

int main() {
    std::cout << biggest(3, 9) << ' ' << biggest(2.5, 1.5) << ' ' << biggest(std::string("pear"), std::string("apple")) << '\n';
    Stack<std::string> history;
    history.push("main.cpp");
    history.push("util.cpp");
    std::cout << history.pop() << ' ' << history.size() << '\n';
    return 0;
}
OUTPUT
9 2.5 pear
util.cpp 1
WHY? Why templates instead of writing three versions?

biggest for int, double and string would be three copies of the same logic, and a bug fixed in one would stay in the others. A template is written once, checked once, and compiled into exactly the versions you use, with no speed penalty. std::vector, std::map and all the containers are templates.

11.11 Move semantics, briefly

Copying a big object is slow. When the original is about to be thrown away anyway, C++ lets you move: steal its insides instead of copying them.

C++
#include <iostream>
#include <string>
#include <utility>
#include <vector>

struct Buffer {
    std::vector<int> data;
    explicit Buffer(size_t n) : data(n, 7) { std::cout << "created " << n << '\n'; }
    Buffer(const Buffer& o) : data(o.data) { std::cout << "COPY\n"; }
    Buffer(Buffer&& o) noexcept : data(std::move(o.data)) { std::cout << "move\n"; }
};

Buffer make() { return Buffer(1000); }

int main() {
    Buffer a(1000);
    Buffer b = a;                    // copies: a is still needed
    Buffer c = std::move(a);         // moves: a gives up its insides
    std::cout << a.data.size() << ' ' << c.data.size() << '\n';
    Buffer d = make();               // returned objects are moved (or built in place)
    std::string s = "text";
    std::string t = std::move(s);
    std::cout << t << ' ' << s.size() << '\n';
    return 0;
}
OUTPUT
created 1000
COPY

0 1000
created 1000
text 0

After a move, the old object is left empty but valid. This is why return of big vectors and strings from functions is cheap in modern C++.

11.13 Threads, in one example

C++
#include <iostream>
#include <mutex>
#include <thread>
#include <vector>

int main() {
    int counter = 0;
    std::mutex m;
    auto work = [&] {
        for (int i = 0; i < 1000; i++) {
            std::lock_guard<std::mutex> lock(m);     // RAII lock: released at the closing brace
            ++counter;
        }
    };
    std::vector<std::thread> pool;
    for (int t = 0; t < 4; t++) pool.emplace_back(work);
    for (auto& t : pool) t.join();
    std::cout << "counter = " << counter << '\n';
    return 0;
}
OUTPUT
counter = 4000
WHAT IF IT WERE DIFFERENT? What if there were no mutex?

Four threads would read, add and write counter at the same time and overwrite each other's work. The result would usually be less than 4000 and different every run: a race condition. The mutex lets only one thread in at a time. lock_guard is RAII again: the lock is released at the closing brace even if an exception is thrown.

11.14 Worked project: a C++ tokenizer

NOVA colours your code with Monaco. But how would you do it yourself? The first step is a tokenizer: cut the text into pieces and label each one. This program does exactly that, using classes, enums, vectors, sets and strings from this chapter.

C++
#include <cctype>
#include <iostream>
#include <map>
#include <set>
#include <string>
#include <vector>

enum class Kind { Keyword, Identifier, Number, String, Comment, Symbol };

const char* name(Kind k) {
    switch (k) {
        case Kind::Keyword: return "keyword";
        case Kind::Identifier: return "identifier";
        case Kind::Number: return "number";
        case Kind::String: return "string";
        case Kind::Comment: return "comment";
        case Kind::Symbol: return "symbol";
    }
    return "?";
}

struct Token { Kind kind; std::string text; };

std::vector<Token> tokenize(const std::string& src) {
    static const std::set<std::string> keywords = {"int", "return", "if", "else", "for", "while", "void", "double", "class", "const", "auto"};
    std::vector<Token> out;
    size_t i = 0;
    while (i < src.size()) {
        unsigned char c = static_cast<unsigned char>(src[i]);
        if (std::isspace(c)) { ++i; continue; }
        size_t start = i;
        if (std::isalpha(c) || c == '_') {
            while (i < src.size() && (std::isalnum(static_cast<unsigned char>(src[i])) || src[i] == '_')) ++i;
            std::string word = src.substr(start, i - start);
            out.push_back({keywords.count(word) ? Kind::Keyword : Kind::Identifier, word});
        } else if (std::isdigit(c)) {
            while (i < src.size() && (std::isdigit(static_cast<unsigned char>(src[i])) || src[i] == '.')) ++i;
            out.push_back({Kind::Number, src.substr(start, i - start)});
        } else if (c == '"') {
            ++i;
            while (i < src.size() && src[i] != '"') { if (src[i] == '\\') ++i; ++i; }
            ++i;
            out.push_back({Kind::String, src.substr(start, i - start)});
        } else if (c == '/' && i + 1 < src.size() && src[i + 1] == '/') {
            while (i < src.size() && src[i] != '\n') ++i;
            out.push_back({Kind::Comment, src.substr(start, i - start)});
        } else {
            ++i;
            out.push_back({Kind::Symbol, std::string(1, static_cast<char>(c))});
        }
    }
    return out;
}

int main() {
    const std::string code = "int total = 42; // the answer\nreturn compute(total, \"hi\");";
    std::map<std::string, int> counts;
    for (const auto& t : tokenize(code)) {
        std::cout << name(t.kind) << "\t" << t.text << '\n';
        ++counts[name(t.kind)];
    }
    std::cout << "---\n";
    for (const auto& [k, n] : counts) std::cout << k << ": " << n << '\n';
    return 0;
}
OUTPUT

WHY? Why enum class and not a plain enum?

A plain enum leaks its names into the surrounding scope (Keyword would be visible everywhere) and converts silently to an int. An enum class keeps names inside (Kind::Keyword) and refuses silent conversion. Fewer clashes and fewer accidents.

  8. Silently creating a new function instead of replacing the base version because of a typo or mismatched signature.
  9. A recipe the compiler uses to generate code for each type; one tested version replaces many copies.
  10. Several threads changing the same data at once give wrong, varying results; a mutex lets one thread in at a time.
  11. It casts to an rvalue so that move constructors/assignments may steal the contents; it does not move anything by itself.
  12. Its names stay inside the enum's scope and it does not convert silently to integers.

Chapter 12CMake: The Recipe Book

12.1 The problem CMake solves

Building a one-file program is easy: g++ main.cpp -o hello.exe. Now imagine a project with 200 files, three libraries, different compilers on Windows, Mac and Linux, debug and release versions, and tests. The command would fill a page and break the moment someone moved a file.

CMake solves this. You write one recipe, CMakeLists.txt, that says what to build. CMake then writes the real build instructions for whatever tool and system you have.

KEY WORD CMake

A build-system generator. It does not compile anything itself. It reads your CMakeLists.txt and produces build files for another tool (Ninja, Make, Visual Studio), which then run the compiler.

NOVA uses CMake because CLion does and because it is the industry standard for C and C++. Every new NOVA project starts with a CMakeLists.txt, and the build button runs exactly two commands: configure and build.

12.2 Your first CMakeLists.txt

This is called an out-of-source build. All the mess (object files, caches, the executable) goes in one folder that you can delete at any time, and your source folder stays clean. 12.5 Libraries and linking

Real projects split into libraries (reusable code) and executables (programs). A target can link to a library.

CMake

Key ideas:

  • target_link_libraries(app PRIVATE geometry) says "app uses geometry". CMake builds geometry first and links it.
  • PUBLIC, PRIVATE, INTERFACE describe who needs a setting:
Keyword Meaning
PRIVATE Only this target needs it.
PUBLIC This target and anything that links to it needs it.
INTERFACE Only the users need it, not the target itself.
WHY? Why does include have PUBLIC on the library?

Anyone who uses geometry must also be able to #include "circle.h". PUBLIC makes the include folder travel along: app and tests get it automatically when they link to geometry. If it were PRIVATE, app would fail with "circle.h: No such file" even though the library built perfectly. It is the most common CMake beginner error.

Chapter 13JSON and Protocols: How Programs Talk

13.1 Why this chapter exists

NOVA is a team of programs: the window, clangd, gdb, the compiler. Programs cannot read each other's minds. They must agree on how to send messages. An agreed way of talking is a protocol. In this chapter you learn the three "languages" NOVA speaks with its helpers: JSON, the Language Server Protocol (LSP) and GDB/MI, plus the terminal's secret code, ANSI escape sequences.

KEY WORD Protocol

A protocol is a set of rules for a conversation between programs: what a message looks like, who speaks first, how to say "I did not understand", and how to know a message has ended.

13.3 Framing: where does one message end?

Programs talk through pipes, which are just streams of bytes with no message boundaries. If you write {"a":1} and then {"b":2}, the reader might receive {"a":1}{"b first and ":2} later. The receiver needs a rule to split the stream into messages. This rule is called framing.

LSP uses a header with the byte length:

Here is a working reader built the same way as the one in NOVA's main.js. It handles messages split at any point.

JavaScript
function makeReader(onMessage) {
  let buf = Buffer.alloc(0);
  return (chunk) => {
    buf = Buffer.concat([buf, chunk]);
    for (;;) {
      const headerEnd = buf.indexOf("\r\n\r\n");
      if (headerEnd < 0) return;                           // header not complete yet
      const m = /Content-Length:\s*(\d+)/i.exec(buf.slice(0, headerEnd).toString("ascii"));
      if (!m) { buf = buf.slice(headerEnd + 4); continue; }
      const len = Number(m[1]);
      if (buf.length < headerEnd + 4 + len) return;        // body not complete yet
      const body = buf.slice(headerEnd + 4, headerEnd + 4 + len).toString("utf8");
      buf = buf.slice(headerEnd + 4 + len);
      onMessage(JSON.parse(body));
    }
  };
}

const frame = (obj) => {
  const json = JSON.stringify(obj);
  return Buffer.from(`Content-Length: ${Buffer.byteLength(json, "utf8")}\r\n\r\n${json}`, "utf8");
};

const feed = makeReader((msg) => console.log("got:", JSON.stringify(msg)));
const wire = Buffer.concat([frame({ id: 1, method: "hello" }), frame({ id: 2, method: "naïve ✓" })]);

// Deliver the bytes in awkward pieces: 7 bytes, 5 bytes, then the rest.
feed(wire.slice(0, 7));
feed(wire.slice(7, 12));
feed(wire.slice(12));
OUTPUT
got: {"id":1,"method":"hello"}
got: {"id":2,"method":"naïve ✓"}
WHY? Why Buffer.byteLength and not text.length?

The header counts bytes, not characters. The text naïve ✓ has 7 characters but 10 bytes in UTF-8, because ï and ✓ take more than one byte. Counting characters would make the reader cut a message in the wrong place and every later message would be garbage. NOVA's main process uses Buffer.byteLength for exactly this reason.

WHAT IF IT WERE DIFFERENT? What if a message is incomplete and the reader parses it anyway?

JSON.parse would throw on half a message, and the stream would be permanently out of step: the next chunk would begin in the middle of something. Returning and waiting for more bytes (as the code above does) keeps the reader in sync.

13.4 JSON-RPC: asking questions across the pipe

LSP messages follow JSON-RPC 2.0. There are three kinds:

Kind Has id? Has method? Meaning
Request yes yes "Please do this and answer me."
Response yes (same id) no (has result or error) The answer to one request.
Notification no yes "FYI", no answer expected.
JSON
{"jsonrpc":"2.0","id":7,"method":"textDocument/hover",
 "params":{"textDocument":{"uri":"file:///c%3A/proj/main.cpp"},"position":{"line":10,"character":17}}}

Reply:

JSON
{"jsonrpc":"2.0","id":7,"result":{"contents":{"kind":"markdown","value":"### function `square`..."}}}

The id is the clever part. Many requests can be in flight at once, and answers may come in any order. The id says which answer belongs to which question.

JavaScript
const pending = new Map();      // id -> function to call with the answer
let nextId = 0;

function request(send, method, params, timeoutMs = 200) {
  return new Promise((resolve) => {
    const id = ++nextId;
    const timer = setTimeout(() => { pending.delete(id); resolve(null); }, timeoutMs);   // give up
    pending.set(id, (result) => { clearTimeout(timer); resolve(result); });
    send({ jsonrpc: "2.0", id, method, params });
  });
}
function onResponse(msg) {
  const cb = pending.get(msg.id);
  if (cb) { pending.delete(msg.id); cb(msg.result); }
}

// A fake server that answers the SLOW request after the FAST one.
const server = (msg) => {
  const delay = msg.method === "slow" ? 60 : 10;
  setTimeout(() => onResponse({ id: msg.id, result: msg.method + " answer" }), delay);
};
const silent = () => { /* never answers */ };

(async () => {
  const [a, b] = await Promise.all([request(server, "slow"), request(server, "fast")]);
  console.log(a, "|", b);                        // each got its OWN answer
  console.log(await request(silent, "ignored"));  // times out -> null
})();
OUTPUT
slow answer | fast answer
null

This is the pattern in lsp.js: a Map of waiting requests, a timeout so a stuck server cannot freeze the editor, and the id to pair answers with questions.

WHY? Why a timeout on every request?

A language server can crash, hang or be busy indexing. Without a timeout, the code that asked "what can I type here?" would wait forever, and a stuck completion popup would be the least of your problems. NOVA gives every request eight seconds (thirty for the first initialize), then simply returns "no answer".

The LSP conversation in order

  1. initialize (request): NOVA says "my project folder is here, and I understand these features". The server answers with its capabilities.
  2. initialized (notification): "Great, let's go."
  3. textDocument/didOpen (notification): "I opened this file; here is its text."
  4. textDocument/didChange (notification): "The text changed." (NOVA sends the whole text, debounced by 120 ms.)
  5. Requests such as completion, hover, definition, references, rename, formatting, codeAction.
  6. textDocument/publishDiagnostics (notification, from the server): "Here are the errors in this file." NOVA turns them into wavy lines.
WHAT IF IT WERE DIFFERENT? What if NOVA forgot to send didChange?

The server would keep analysing the old text. Completion would suggest names that no longer exist, hover would point at wrong lines, and error underlines would sit in the wrong places. The editor and server must always agree about the file's contents.

The off-by-one trap

LSP positions are 0-based (line 0 is the first line). Monaco's are 1-based. NOVA converts at the border:

JavaScript
const toPos = (p) => ({ line: p.lineNumber - 1, character: p.column - 1 });
const fromRange = (r) => new monaco.Range(r.start.line + 1, r.start.character + 1, r.end.line + 1, r.end.character + 1);

Forget the conversion and every underline lands one line too high.

13.5 GDB/MI: talking to the debugger

gdb has a human interface (type print x). It also has a machine interface called GDB/MI designed for programs like NOVA. You start gdb with --interpreter=mi3 and talk to it in lines of text.

First char Kind Example
^ Result of a command ^done,bkpt={number="1"}
* Async event (program state changed) *stopped,reason="breakpoint-hit"
= Notification (breakpoint added, library loaded) =breakpoint-modified,...
~ Console output text ~"Hello\n"
@ The program's own output @"Total: 5\n"
& gdb's log &"print x\n"

A command may begin with a token (a number) so you can match the result: you send 7-exec-next and gdb answers 7^running.

After the class name, data is a list of key="value" pairs, where a value can be a string, a {tuple} or a [list]. Here is a working parser that is the same logic as NOVA's debug.js:

JavaScript
function miCString(p) {
  if (p.s[p.i] !== '"') return "";
  p.i++;
  let out = "";
  while (p.i < p.s.length) {
    const c = p.s[p.i++];
    if (c === '"') break;
    if (c === "\\") {
      const n = p.s[p.i++];
      if (n === "n") out += "\n"; else if (n === "t") out += "\t"; else out += n;
    } else out += c;
  }
  return out;
}
function miValue(p) {
  const c = p.s[p.i];
  if (c === '"') return miCString(p);
  if (c === "{") { p.i++; return miResults(p, "}"); }
  if (c === "[") {
    p.i++;
    const arr = [];
    while (p.i < p.s.length && p.s[p.i] !== "]") {
      if (/^[\w-]+=/.test(p.s.slice(p.i))) {          // a named item such as frame={...}
        const eq = p.s.indexOf("=", p.i);
        const k = p.s.slice(p.i, eq);
        p.i = eq + 1;
        arr.push({ [k]: miValue(p) });
      } else arr.push(miValue(p));
      if (p.s[p.i] === ",") p.i++;
    }
    p.i++;
    return arr;
  }
  return "";
}
function miResults(p, close) {
  const o = {};
  while (p.i < p.s.length && p.s[p.i] !== close) {
    const eq = p.s.indexOf("=", p.i);
    if (eq < 0) break;
    const k = p.s.slice(p.i, eq);
    p.i = eq + 1;
    o[k] = miValue(p);
    if (p.s[p.i] === ",") p.i++;
  }
  if (close && p.s[p.i] === close) p.i++;
  return o;
}
function miParseLine(line) {
  const m = /^(\d*)([\^*=~@&])(.*)$/.exec(line);
  if (!m) return { t: "raw", text: line };
  const [, tok, ch, rest] = m;
  if ("~@&".includes(ch)) return { t: ch, text: miCString({ s: rest, i: 0 }) };
  const ci = rest.indexOf(",");
  const cls = ci < 0 ? rest : rest.slice(0, ci);
  const data = ci < 0 ? {} : miResults({ s: rest.slice(ci + 1), i: 0 });
  return { t: ch, tok: tok ? +tok : null, cls, data };
}

WHY? Why write a parser instead of using a regular expression?

MI values nest: a tuple contains a list that contains tuples. Regular expressions cannot match arbitrarily deep nesting. A parser that calls itself for each nested level (miValue calls miResults, which calls miValue...) handles any depth. It is the same recursive descent idea as the calculator in Chapter 8.

13.6 The terminal: bytes and escape codes

A terminal is a program that shows a grid of characters and sends your key presses to a shell. A shell program cannot draw colours or move the cursor with function calls, so it sends special byte sequences hidden inside its text, beginning with the character ESC (code 27, written \x1b). These are ANSI escape sequences.

JavaScript

console.log(JSON.stringify(coloured));

Common ones: ESC[31m red text, ESC[0m reset all, ESC[2J clear screen, ESC[10;5H move the cursor to row 10, column 5. The xterm.js library inside NOVA understands them all and draws the result.

WHY? Why does NOVA use a PTY for the terminal instead of simple pipes?

Programs behave differently when they know a human is watching. Many check "is my output a terminal?" and, if not, turn off colours, buffer their output and refuse to ask questions. A PTY (pseudo-terminal; on Windows, ConPTY) pretends to be a real terminal, so shells, git, Python and text-mode programs behave normally. With plain pipes, PowerShell would print no prompt and interactive tools would not work.

IN PLAIN WORDS The buffered printf

The Run panel uses pipes, not a PTY, so a C program's printf("Enter a number: ") may stay hidden in the program's own buffer until it ends. C's standard library buffers output fully when it is not connected to a terminal. NOVA fixes this by quietly adding a tiny header to the build, -include nova_unbuf.h, which calls setvbuf(stdout, NULL, _IONBF, 0) to turn the buffering off. This is why prompts appear instantly in NOVA. A small trick, but it needed a good understanding of how protocols between a program and its viewer really work.

13.7 Designing your own protocol: lessons

  1. Frame your messages. Never assume a read equals a message.
  2. Give requests ids. Answers arrive out of order.
  3. Add timeouts. The other side can hang or crash.
  4. Separate requests from notifications. Not everything needs an answer.
  5. Be strict when sending, tolerant when receiving. NOVA ignores unknown messages instead of crashing.
  6. Make states explicit. The debugger moves between not debugging, running, paused, ended:
WHY? Why model the debugger as states?

You can only step when the program is paused. Pressing Step while it is running makes no sense. Writing the states down means every button simply asks "what state am I in?" instead of a tangle of true/false variables. NOVA's dbgUi function sets all the toolbar buttons from the two flags D.on and D.running.

Loading Monaco

Monaco is delivered as an old-style module system called AMD, started by a file named loader.js. In index.html you add:

HTML
<script src="../node_modules/monaco-editor/min/vs/loader.js"></script>

Then, in JavaScript (this is NOVA's real boot function, trimmed):

JavaScript
async function boot() {
  hydrateIcons();
  S.settings = { ...DEFAULTS, ...(await nova.loadSettings()) };
  applyTheme();
  S.tools = await nova.detectTools();
  updateToolchain();

  const b = new URL('../node_modules/monaco-editor/min/', location.href).href;
  window.MonacoEnvironment = {
    getWorkerUrl: () => 'data:text/javascript;charset=utf-8,' + encodeURIComponent(
      `self.MonacoEnvironment={baseUrl:'${b}'};importScripts('${b}vs/base/worker/workerMain.js');`)
  };
  require.config({ paths: { vs: b + 'vs' } });
  require(['vs/editor/editor.main'], () => { initMonaco(); wireUI(); renderRecent(); renderWelcomeState(); });
}

Walk through it:

  • { ...DEFAULTS, ...(await nova.loadSettings()) } merges two objects. Saved settings win; anything missing falls back to the defaults. (The spread operator from Chapter 8.)
  • new URL('../node_modules/...', location.href).href builds the full address of the Monaco folder, relative to where index.html lives.
  • MonacoEnvironment.getWorkerUrl tells Monaco where its workers are. A web worker is a background thread. Monaco uses workers so that heavy jobs (like checking JSON) never freeze typing.
  • require(['vs/editor/editor.main'], callback) loads Monaco, then runs our callback when it is ready.
WHY? Why the strange data: URL for the worker?

Workers must normally be loaded from a normal web address, but our page is loaded from a file (file:///...), where browsers refuse to start a worker straight from another file. The trick: create a tiny script as text inside a data: URL that simply says "import the real worker file". The browser accepts that. It is a known workaround and the single most puzzling line in the whole project. Without it the editor still appears, but silently loses features and the console fills with worker errors.

WHAT IF IT WERE DIFFERENT? What if initMonaco ran before Monaco finished loading?

monaco would be undefined and the first line that used it would crash with "monaco is not defined". That is why everything that needs Monaco is inside the callback. This is the same lesson as the async/await section: wait for the thing you depend on.

WHY? Why taskkill with /T?

The renderer's side: a race condition and its cure

The window starts a process, gets an id, and then registers a listener for that id. But output could arrive in the tiny gap between. NOVA solves it with a holding area:

JavaScript
const sinks = {}, early = {};
nova.onData(m => { const s = sinks[m.id]; if (s) s.data(m); else (early[m.id] = early[m.id] || []).push({ t: 'd', m }); });
nova.onExit(m => { const s = sinks[m.id]; if (s) s.exit(m.code); else (early[m.id] = early[m.id] || []).push({ t: 'x', m }); });

async function spawnProc(cmd, args, cwd, sink, opts) {
  const id = await nova.start(cmd, args, cwd, opts);
  const wrapped = { data: sink.data, exit: (code) => { delete sinks[id]; sink.exit(code); } };
  sinks[id] = wrapped;
  const pend = early[id] || []; delete early[id];
  for (const ev of pend) ev.t === 'd' ? wrapped.data(ev.m) : wrapped.exit(ev.m.code);
  return id;
}
WHAT IF IT WERE DIFFERENT? What if early output were just dropped?

A program that prints and exits instantly (like "Hello, NOVA!") could finish before the window registered its listener. Its output and exit code would vanish, and the Run panel would stay empty. This kind of bug appears only sometimes, which makes it extremely hard to find. A race condition is two things racing to happen first. The early buffer removes the race.

The pipeline: build, check, run

JavaScript
async function runPipeline(steps, label) {
  if (S.running) { await stopRun(); }

16.1 Step 9: Search, Search Everywhere and the command palette

Goal. Find text across the whole project, jump to any file or symbol by typing a few letters, and run any action by name.

Business rules.

  1. Finding a file must take about two seconds no matter how big the project is.
  2. Typing "shp" should find shapes.cpp: the letters must match in order, not necessarily next to each other (this is called fuzzy matching).

Find in Files (done by the main process)

The window sends the query; the main process walks the folders and reads the files; it sends back a list of matches. Doing the heavy work in the main process means the window never freezes.

JavaScript
ipcMain.handle('fs:grep', (_e, root, query, opts = {}) => {
  const files = []; walk(root, files);
  const results = [];
  const src = opts.regex ? query : query.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
  const re = new RegExp(opts.word ? `\\b${src}\\b` : src, opts.case ? '' : 'i');
  for (const f of files) {
    const buf = fs.readFileSync(f); if (buf.includes(0)) continue;      // skip binaries
    buf.toString('utf8').split(/\r?\n/).forEach((ln, i) => {

    });
  }
  return results;
});

Three protective details, each a business rule in disguise:

  • The long replace escapes special characters, so searching for a.b or (x) means the literal text, not a pattern. (Unless the user ticks the regex box.)
  • Files over 2 MB and binary files are skipped, so one giant log cannot freeze the search.
  • Results stop at 2000. Nobody reads more, and a million-item list would crash the display.

Fuzzy matching

This is the real scoring function from NOVA's app.js. You can run it.

JavaScript
function fuzzy(q, s) {
  q = q.toLowerCase(); const t = s.toLowerCase(); let i = 0, score = 0, last = -2;
  for (let j = 0; j < t.length && i < q.length; j++) {
    if (t[j] === q[i]) {
      score += (j === last + 1 ? 5 : 1) + (j === 0 || /[\/\\._\- ]/.test(t[j - 1]) ? 4 : 0);
      last = j; i++;
    }
  }
  return i === q.length ? score - t.length * 0.01 : -1;
}

How it scores:

  1. Walk through the name; every time the next wanted letter is found, give a point.
  2. +5 bonus if it directly follows the previous matched letter (a run like "sha").
  3. +4 bonus if it begins the name or follows a separator (/ \ . _ - space): word starts matter.
  4. A tiny penalty for length, so shorter names rank above longer ones with the same match.
  5. If not all the letters were found, return -1: no match.
WHY? Why such a simple formula?

Because it runs on thousands of names on every keystroke and must feel instant. Real IDEs use cleverer scoring, but this 8-line version captures what users expect: starts of words and unbroken runs win. Simple, fast and good enough is often the right engineering answer.

Talking in requests

The JSON-RPC client is tiny:

JavaScript
function lspRequest(method, params, timeout = 8000) {
  if (!LSP.on) return Promise.resolve(null);
  return new Promise((res) => {
    const id = ++LSP.id;
    const t = setTimeout(() => { LSP.pending.delete(id); res(null); }, timeout);
    LSP.pending.set(id, (r) => { clearTimeout(t); res(r); });
    lspSend({ id, method, params });
  });
}

It is the request/pending code from Chapter 13, with one extra line: if clangd is not running (LSP.on false) the answer is instantly null, so the editor carries on as normal. That is rule 3 in one line.

16.4 Step 12: The debugger

Goal. Stop a running program at breakpoints, look at its variables, and step through it line by line.

Business rules.

  1. Breakpoints are set by clicking the margin, and can be added or removed while the program runs.
  2. The debugger builds first (with -g); if the build fails it must not start.
  3. When the program stops, the editor must show exactly where: highlighted line, arrow, and the right file.
  4. Buttons must only be enabled when they make sense.
  5. Crashes (like a null pointer) must be reported in plain words.

Starting gdb and talking MI

JavaScript
async function dbgStart(exe, cwd) {
  const r = await nova.gdbStart(exe, cwd, []);
  if (r.error) return toast('Could not start gdb: ' + r.error, 'error');
  Object.assign(D, { on: true, running: false, frames: [], vars: [], sel: 0, bpNum: new Map(), exe, prevVars: new Map() });

  await dbgCmd('-gdb-set confirm off');
  await dbgCmd('-gdb-set new-console ' + (S.settings.debugExtConsole === false ? 'off' : 'on'));
  await dbgCmd('-environment-cd ' + miq(fwd(cwd)));

}

Each await dbgCmd(...) sends one MI command and waits for its numbered answer (the token matching you saw in Chapter 13). The setup commands are rules in disguise:

  • breakpoint pending on: a breakpoint in code that is not loaded yet is accepted instead of refused.
  • confirm off: gdb never stops to ask "are you sure?", which would freeze our machine-driven conversation.
  • new-console on: your program gets its own window, so it can read the keyboard.

What. Edit and build code that lives on another computer.

First steps. Use SSH to run commands remotely (the ssh program, or Node's ssh2 library), replace fs:read and fs:write with versions that go over SSH or SFTP, and start clangd and gdbserver on the remote machine. Study how VS Code Remote and JetBrains Gateway divide work between a thin local UI and a remote "backend". It is a big project: security and network failure are the real topics.

17.14 Project 12: Grow up: TypeScript and a bundler

NOVA is plain JavaScript on purpose: nothing to install, nothing between you and the code. As a project grows to ten thousand lines, TypeScript (JavaScript with types) catches whole families of mistakes before you run the program, and a bundler (such as esbuild) combines files and enables real import statements.

First steps. Rename lsp.js to lsp.ts. Add npm install --save-dev typescript. Describe the shapes you use (interface Tab { path: string; dirty: boolean; ... }). Let the compiler list every place where the shape is misused. Then add esbuild to produce the files the window loads.

17.15 How to learn from here

  • Read other people's code. Open the source of a small, well-loved tool and trace one feature from the click to the result, as you did with Run in this book.
  • Rewrite something small three times. The first version teaches you the problem. The second shows you what you misunderstood. The third is good.
  • Keep a "bugs I have met" file. In this book you saw several real ones: the define clash, the hidden attribute, the path-casing duplicate, the TDZ race. Each bug you remember is a shield for life.
  • Teach it. Explain a chapter to a friend. Where you stumble is what you have not understood yet.
